<a id="inspect-the-installation" />

## 1. Inspect the installation

```shell
kast status
```

Read registrations and live service state on their own. Registration shows an installed integration. It does not prove a ready workspace or live semantic authority.

<a id="upgrade" />

## 2. Upgrade a compatible installation

Wait for active calls to finish. Start the upgrade after you save source work.

```shell
kast upgrade
```

Upgrade stops owned services and interrupts sessions. After success, restart IDEA and clients. Then start fresh sessions and calls. Upgrade does not start a Codex broker. Its MCP session starts IntelliJ preparation when the client connects. If the Codex plugin is installed, run `kast plugin codex` to refresh its cached files.

<Accordion title="Upgrade Control without replacing Host">
  Control supplies the command, coordinator, agent adapters, and sessions. Host supplies the IDEA plugin and semantic runtime.

  ```shell
  kast upgrade --control-only
  ```

  This command needs a running compatible Host. It keeps IDEA and its plugin files. Control sessions can stop during the upgrade.

  Kast checks the Host contract before shutdown and after startup. If it fails, Kast restores the previous Control or reports the need for recovery.

  [Compatibility](/reference/compatibility) checks protocol, registry, schema, supported features, and IDEA admission. Equal version numbers alone do not prove that components work together.
</Accordion>

<Accordion title="Load a Host update">
  For Host-only installation, use the public installer with `--host-only --version <host-version>`. Restart IDEA to load the plugin.

  Hosted changes use a private local endpoint and native workspace admission. Installation does not create approval keys.

</Accordion>

<a id="stop-and-reinstall" />

## 3. Stop and reinstall a recorded version

Before stop, quit the selected IDEA instance. Close affected agent connections. Then request retirement and recovery of the recorded version.

```shell
kast stop --json
kast reinstall --json
```

`stop` fences new calls and automatic restart before retirement. It disables the coordinator. It waits up to 30 seconds for recorded calls and MCP sessions.

The installed payload, settings, and registrations stay in place. `--force` asks to retire recorded tool processes. Their process identities have to pass admission first.

Before a signal, Kast checks PID start time, main class, and installed library digests. If IDEA is live, it returns `HOST_RESTART_REQUIRED`.

If shutdown rejects, keep the fence. Payload replacement cannot continue through failed shutdown.

After shutdown succeeds, `reinstall` installs the recorded version. It removes the exact owned shutdown fence. It restores supported integrations. It does not start a coordinator. Recorded Codex registrations migrate through the plugin owner.

If payload completion fails, Kast keeps the fence and reports its stage. Inspect `kast status --json` before another recovery try.

The published installer can resume a valid shutdown. Routine replacement first retires the prior installation. It then checks which state to keep.

If retirement or payload replacement fails, recovery can restore the predecessor. The result reports that recovery outcome.

### Lifecycle result contract

JSON stdout reports `STOPPED`, `REINSTALLED`, `REJECTED`, or `REINSTALLATION_PENDING`. Stage evidence goes to stderr. A failed result exits with code 1. Force reinstall reports `RESET_INSTALLED` after payload and fence work is complete. That result claims no service generation or readiness.

The installed `management-lifecycle.schema.json` owns exact variants. Older payloads without fence capability reject before lifecycle effects.

### Workspace recovery after replacement

A later authorized demand can check a missing or mismatched Host again. After a Host update, restart IDEA before new semantic admission.

Setup history does not prove readiness forever. Its lookup store has a fixed size. It can reclaim older final records while keeping results that are still held.

A reclaimed ID returns `UNKNOWN_OPERATION`. That result cannot tell an expired record apart from an ID that Kast never issued.

A recovery step does not replay a write. [Lifecycles](/reference/lifecycles) explains project setup and how requests end.

<a id="force-reset" />

## 4. Reset only after ownership recovery fails

Force reset erases installed state and has no rollback after erasure. Use it only when that reset scope matches your recovery need.

```shell
kast uninstall --force --json
kast reinstall --force --json
```

Reset fences startup and moves the installation aside. It then retires processes within its scope. If retirement fails, it keeps a recovery path.

Shared IDEA and Gradle processes remain under your control. The outer lock files stay in place.

Reset removes `$HOME/.kast` state, `$HOME/.local/share/.kast-*` artifacts, and the public command.

It unlinks symlinks without reading their targets. It rejects filesystem roots, HOME, and ancestors of HOME as targets to delete.

Force reinstall selects the latest release from the saved channel. It installs Control and Host and repairs valid recorded connections.

Success returns `RESET_INSTALLED`, version, installation path, and command path. Restart IDEA and affected clients after success.

The public installer uses this reset with `--force`. A developer installation requests it by default after archive admission.

`--dry-run` keeps files and registrations. A version-pinned installation can use newer recovery code whose checksum passed admission. It still keeps the selected installation version.

### Reset outcomes

The closed variants include `REMOVED`, `RESET_INSTALLED`, `RESET_REINSTALLATION_PENDING`, `RESET_RETAINED`, `RESET_RECOVERY_REQUIRED`, and `RESET_REJECTED`.

If installation fails, the result is `RESET_REJECTED`. If payload or fence work fails after staging, it is `RESET_REINSTALLATION_PENDING`. Failed outcomes exit with code 1.

If a result reports `recoveryPath`, keep that path. Check the named failed stage before another reset.

## Change agents

```shell
kast connect pi
kast disconnect copilot
```

Restart a disconnected client to unload its integration. Other clients and the shared daemon keep their own lifecycle.

## Uninstall

```shell
kast uninstall
```

If removal fails, keep ownership and recovery evidence. Resolve its named cause before another try.

## Explicit workspace control in the hosted App Server

Hosted `workspace_lifecycle` can inspect, present, release, or close a project. Direct MCP and Tool RPC omit that tool.

Before a project action, check the installed schema and the authority it needs. Disconnect, release, and project closure have different effects.
