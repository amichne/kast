A query result contains semantic facts and their coverage. It also reports producer progress and how much output was shown. Each field answers a distinct part of the source question.

Read these facts in order before a conclusion:

1. Read the tool-call outcome and the semantic status.
2. Read the searched scope and completion interpretation.
3. Examine the returned facts with their source evidence and stated limits.
4. Use the issued handles if more rows or evidence remain.

A full page can belong to an incomplete answer. A short preview can belong to a complete answer.
Page size alone proves neither case.

<a id="read-coverage-before-a-claim" />

## Semantic status and coverage

| Status | Meaning |
| --- | --- |
| `complete` | Declared scope covered. |
| `qualified` | Stated limitations or unfinished work remain. |
| `rejected` | Input or state requirements prevented completion. |

Each fact keeps the scope that produced it and its stated limits. Qualified output with no rows cannot prove absence.

Complete coverage means that the scan finished within the declared supported domain. Semantic completion also needs all the model's proof rules to be met.

<a id="read-an-automatic-query" />

## RUN completion

The query response uses `kast.query.run.v9`. Host and Control must agree on that contract.

Every public run uses `COMPLETE_ONLY` within `COMPILER_RESOLVED_STATIC_V1`. The work must finish without item failures or omitted evidence.

`TRACE` from source symbols reports `SOURCE_RELATIONSHIPS` with `callbackEffects: EVIDENCE_ONLY`. Exact source relationships remain usable when callback execution has explicit gaps. The result keeps each gap with its callback evidence. Retained pages preserve that interpretation, including pages without callback evidence.

This interpretation permits source filters and deduplication before `TRACE`. An explicit relation operation, traversal, composition, retained source, or impact source keeps the stricter callback graph proof.

Unresolved compiler mappings, missing source membership, stale dependency evidence, and exhausted grants still prevent completion.

Impact investigations also keep their original ledgers intact and meet all proof rules. The model does not prove that code ran or that a path can run.

### Two different meanings of missing output

Suppose a complete query produces five rows, but its preview shows two.
The remaining three rows are output to read through the issued handle. They are not unfinished search work.

Now suppose a query stops before it proves completion and keeps two rows as rejection evidence.
Those rows remain useful facts with their original limits. The last evidence page does not turn the rejected answer into a complete answer.

These numbers illustrate the distinction. They are not a captured Kast response.

<a id="read-evidence-from-a-completion-rejection" />

### Completion rejection evidence

`COMPLETION_UNPROVEN` keeps the specific cause and original coverage. If retention succeeds, its evidence includes a result reference and preview. It also includes the original question and `nextQuery`.

Copy `nextQuery` to use its public `READ_RESULT` arguments. The canonical `question` has a different grammar. It cannot replace those arguments.

`policyProgress` is `EVIDENCE_ONLY`. Reads of that result keep `POLICY_REJECTED_EVIDENCE`. This holds even if the original scan coverage is complete.

A historical checkpoint records producer progress. It grants no right to run new public semantic work.

If supplied, `seedQuery` starts a new investigation from proved preview identities. It does not cover rows left out or scope left unfinished.

If retention fails, the result reports the storage cause. It does not invent a handle. `RETENTION_UNAVAILABLE` can keep a complete scan even if needed storage is not available.

### Row and evidence positions

| Response field | Meaning |
| --- | --- |
| `invocation.accumulated_row_count` | Rows produced so far across admitted pages. |
| `invocation.preview.type` | `INLINE` includes every produced row. `PREFIX` includes an ordered preview. |
| `invocation.preview.row_count` and `encoded_bytes` | The row count and UTF-8 byte count of the encoded preview `items` array. |
| `invocation.stop.type` | Typed reason for the stop, with evidence for a failure. |
| `retention` and `next_cursor` | Issued result reference and position for more saved rows. |
| `evidence_window` | Evidence positions: `start`, `end`, and `total`. `MORE` means there is more evidence. `FINAL` reaches the saved end. |

The preview uses `INLINE` if all produced rows fit. `PREFIX` shows an ordered portion that fits the row and encoded-byte limits.

If retention succeeds, use the retained reference and cursor with `READ_RESULT` to read more rows. It does not replay semantic work.

A preview that leaves rows out does not change producer coverage. A complete retained result stays complete as you read its pages.

Row counts describe logical output rows, not graph nodes, connections, or evidence observations. Those tables can contain several entries for one row.

Row and evidence cursors move on their own. A page with only evidence can advance `evidence_window`. Its row cursor can stay unchanged.

Evidence appears in this order:

1. Failures.
2. Omissions.
3. Walk observations.
4. Reference observations.
5. Discovery observations.
6. Relation observations.

`evidence_window.type: MORE` names remaining evidence. Its `end` supplies the next `evidence_cursor`.

After the last row, the row cursor stays at `invocation.accumulated_row_count` while evidence advances. `FINAL` marks the stored evidence end.

<a id="follow-progress-not-row-count" />

## Producer progress and output progress

| Operation | Advances | Handle |
| --- | --- | --- |
| `RESUME` | Shows output already produced | Issued `query-output:v1` token |
| `READ_RESULT` | Shows stored rows and evidence | A result reference. Row and evidence cursors move on their own. |

Public `RUN` owns semantic execution. Public `RESUME` uses an issued `query-output:v1` token. It only shows output already produced.

`READ_RESULT` shows stored rows and evidence from the identified retained result. These rows cannot change. Neither action visits new files or restarts discovery.

The issued `next_action` names a valid output read or recovery step. Row count alone cannot prove that work is complete or output is available.

`retention_unavailable` records loss of the remaining suffix. A missing continuation does not prove a complete answer.

<a id="carry-the-correct-handle-forward" />

## Handle families

| Handle | Use |
| --- | --- |
| Exact symbol `ref` | Fresh `SYMBOL_REFS` query with current identity checks. |
| Retained-result reference | `RESULT`, composition, or `READ_RESULT`. |
| Row ID | Select a row from its owning result. |
| Issued output continuation | Output-only `RESUME`. |
| Result cursor | Page stored rows. |

An anonymous `candidateSelector` supplies `READ_SOURCE.candidateRef`. An evidence cursor selects a position in the distinct evidence sequence.

Keep each handle's issued spelling and owning resource. Equal names, paths, or opaque tokens do not replace canonical identity checks.

## Compact and detailed output

Compact output is the default. `verbose: true` adds execution details without a stronger semantic answer.

When `relation_graph` is present, compact rows use table IDs instead of repeating symbol and relationship documents:

| Row or table field | Join target |
| --- | --- |
| `exact-symbol-node.node` | `relation_graph.nodes[].id` |
| `exact-symbol-node.connections[]` | `relation_graph.connection_witnesses[].id` |
| Direct connection `source` and `target` | `relation_graph.nodes[].id` |
| Reference-backed connection `witness` | `relation_graph.witnesses[].id` |
| `reference-edge.witness` | `relation_graph.witnesses[].id` |
| Witness `target` and declaration-owned `ownership.declaration` | `relation_graph.nodes[].id` |

Each node keeps its exact reference in `node.symbol.selector`. Pass that selector, not the node ID, to a fresh `SYMBOL_REFS` query.
Node, connection, and witness IDs describe evidence within `relation_graph.basis`; they are not live declaration selectors.

`relation_graph.detail` supplies arguments for a detailed retained read. Table joins recover compact descriptions; they do not advance row or evidence cursors.

```json
{
  "request": {
    "type": "RUN",
    "source": {"type": "SEARCH_DECLARATIONS", "declarationName": "QueryStepSyntax"},
    "terminalStep": {"type": "EMIT"}
  },
  "verbose": true
}
```

`knownMinimum` counts logical final output that Kast has proved. It includes rows already sent. It does not count candidates before filters or pages left.

### Byte limits and callback proof

The final response has a limit on encoded bytes. Kast uses a distinct, conservative count for the storage held by detached callback proof.

A small row count does not prove that either allowance has enough capacity. A byte rejection keeps its scan state and proof still needed.

The IDEA `kast_semantic_read` receipt reports retention allowances and what storage was admitted or required. It also reports specific decision counters.

That receipt counts proof storage with a conservative charge. It does not measure heap use or encoded output bytes.

## Value-path relationships

Full paths and compact findings include `classification`.

| Classification | Meaning |
| --- | --- |
| `ESTABLISHED` with `EXACT` | Every admitted step preserves the tracked value. |
| `ESTABLISHED` with `DERIVED` | The path includes established content construction. |
| `NOT_ESTABLISHED` | The record identifies the first step without established value correspondence. |

A later exact step keeps earlier derivation or missing proof.
Compiler, reviewed-library, and model evidence keep their distinct authority.
Admitted modeled connections keep their models and qualifications.
A modeled step alone yields `NOT_ESTABLISHED`.

A Kotlin string template consumes the established embedded result.
A `String?` value contributes content only when its value is non-null.
Its null alternative constructs literal `null` without source-content contribution.
A null-only result keeps an explicit constant-construction record.
Each repeated entry keeps its own occurrence, even when entries reach one requested site.

A constant getter or conversion can discard its input.
Its own String result can still contribute content.
An implicit object conversion uses the selected `kotlin.Any.toString()` member or override.
An unsupported conversion keeps its exact entry and selected member evidence.

## Saved state and identity

Fresh `RUN` queries can reacquire exact references under current compiler authority. This does not refresh earlier rows or evidence.
Public `READ_SOURCE` instead checks the issued snapshot, including when `candidateRef` contains an exact reference. It does not reacquire that reference.

Retained results and output continuations need their original workspace, owner, read state, and lifetime.

Changed epochs, owner retirement, expiry, or eviction can block reuse. Reading output cannot move an answer to another epoch.

[Staleness](/reference/staleness) explains checks for reuse. [Composition](/reference/composition) keeps the stated limits of each input. It rejects absence claims that lack proof.

## Procedures and source evidence

[Read retained evidence](/how-to/read-retained-evidence) gives cursor steps. [Lifecycles](/reference/lifecycles) names distinct owners for execution, settlement, and transport delivery.

Direct MCP puts the operation document in `result.structuredContent`. Tool RPC and completed hosted calls carry `document`.

MCP transport rejection uses a distinct envelope: `result.isError` is `true`, and `result.structuredContent` contains `type: "MCP_REJECTED"`, `status: "rejected"`, and `error`.
For an overlapping invocation, `error.code` is `INVOCATION_IN_PROGRESS`. This is not a canonical semantic rejection or evidence that the active query failed.
[MCP concurrency](/reference/limits#mcp-concurrency) describes the per-connection limit and recovery.

`health_check` has its own readiness shape. [The source map](/reference/source-map#query-execution-and-retention) identifies the query and retention owners.
