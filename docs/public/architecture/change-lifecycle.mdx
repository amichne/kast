A source change needs an exact target. It also needs authority for the source state in the plan. A successful read alone does not authorize a write.

1. Planning binds a supported intent to an exact target and preimage: the source state before the write.
2. Applying a plan starts with its stored identity. Kast checks the source again before it admits the write.
3. The write uses admitted authority and records recovery state.
4. Checks after the write produce a result. If a later phase fails, a source effect can still need recovery.

The diagram shows the phases in order. It does not list every encoded result kind.

<Warning>
  A missing response does not prove that no write occurred. Keep the receipt and inspect current source before another write.
</Warning>

## What verification proves

The receipt names the plan, phase, new state, and evidence. Its checks apply to the reported scope.

The public tools can add a declaration or replace a supported block body. They do not refactor arbitrary code. They do not prove that the project builds.

[Make a targeted change](/reference/change) gives the procedure and recovery steps. [Generated callable schemas](/reference/schemas) define exact inputs and result variants.
