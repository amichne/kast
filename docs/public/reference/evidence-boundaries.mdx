A Kast answer states what the compiler proved for one question. Identity, coverage, completion, and runtime execution are distinct facts.

Kast keeps those facts distinct because each supports a different claim. A stronger claim needs its own evidence.

## Choose the claim

| Question | Evidence to examine | Limit |
| --- | --- | --- |
| Which declaration is this? | Exact identity, signature, and location. | One identity does not prove that discovery found every match. |
| Are there no matches? | Complete coverage of the requested supported scope. | An unfinished search cannot prove absence. |
| Which callback route is supported? | Supply, argument mapping, and an admitted invocation route. | A static route does not prove runtime execution. |
| Did the project behavior change? | The change receipt and the project's tests. | A receipt alone does not prove the whole project builds. |

These questions need distinct evidence. [Program tracing](/reference/program-tracing) shows how the callback route keeps each source owner.

## Exact facts are not the same as exhaustive coverage

An exact identity proves one declaration. Complete coverage also proves that the scan finished. This claim applies within the declared supported scope.

Qualified coverage keeps the proved declaration and its stated limits. More matches or unfinished proof can remain.

A complete scan with no matches can prove absence within its supported scope. An empty qualified result cannot prove absence.

A completion rejection reports proof still needed for the execution, graph, or investigation. A finished scan alone cannot supply that proof.

Scope leaves out sources that the question does not admit. Libraries and generated sources keep their stated limits. So do languages that are not supported and bodies that are not available.

An exact occurrence can still help when complete proof fails. Keep its stated limits with each later use.

## Evidence delivery cannot strengthen a proof

A preview shows the output that fits. It does not change the original question.

`RESUME` and `READ_RESULT` show produced facts. They do no new semantic work. A final page cannot supply callback or investigation proof that is still missing.

`retention_unavailable` records loss of remaining output. Absence of a token does not prove complete coverage.

## The original state constrains reuse

Retained evidence belongs to its original workspace, IDEA owner, read state, and lifetime. If the source state changes, it needs a new answer.

An exact reference can gain fresh compiler authority under its identity policy. This does not move an old retained result to the new state.

[Staleness](/reference/staleness) explains that difference. [Results](/reference/responses) defines handles and presentation progress.

## Read relationship and edit evidence

A call resolved by the compiler proves a static relationship in source. It does not prove that code ran. It does not prove that a branch can run or how often a call runs.

Supplying a callback does not prove a call. The named body that contains a call is not always its named caller. [Program tracing](/reference/program-tracing) identifies the necessary path evidence.

A verified edit receipt proves the source effect it reports within the scope it checked. Project tests and builds prove distinct behavior.

An uncertain write needs source and recovery evidence before another write. [Change recovery](/reference/change#read-the-receipt) supplies that procedure.
