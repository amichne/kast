The public management verbs are `config`, `install`, `status`, `stop`, `versions`, `upgrade`, `uninstall`, and `reset`.
Semantic commands use the same installed managed runtime through the CLI and MCP.
See [installation limits](/reference/installation) for the current implementation and native acceptance status.

<a id="inspect-the-installation" />

## 1. Check the installation

```shell
kast status --json
kast status --workspace /absolute/project/path --json
kast status --all --json
```

The default scope is the current workspace. `--workspace` selects an exact workspace; `--all` selects all recorded workspaces.
These selectors are mutually exclusive. Use `--all` outside a project to inspect the whole installation.
Status reads local evidence without starting Java, granting trust, repairing state, or contacting release servers.
If the coordinator runs, status asks it for its version. Status starts no coordinator and no Host.

| Field | Meaning |
| --- | --- |
| `loadedVersion` | Version of the running coordinator. `COORDINATOR_NOT_RUNNING` and `COORDINATOR_STARTING` name the other known states. |
| `installedBuild` | Recorded build identity on disk. |
| `product` | Exact installed product composition. |
| `updatePolicy` | Channel or pinned-build policy. |
| `unresolvedTransaction` | Unfinished installation work. |
| `workspaces` | Scoped workspace records, runtime digests, and Host observations. |
| `applicationHost` | For a managed product, unavailable with `WORKSPACE_SCOPED`; inspect `workspaces` instead. |

Observations have a `state` of `VERIFIED` or `UNAVAILABLE`, with a `value` or `reason`.
An unavailable observation is not proof of absence. A loaded Host is not proof of semantic readiness.

Each recorded workspace exposes its creation-time `dependencySharing` policy and canonical `gradleHome`.
`savedDependencyConfiguration` compares both with saved installation and workspace configuration, without ambient environment overrides.
Its verified value is `MATCHES_CREATION` or `DIFFERS_FROM_CREATION`; failed comparison remains unavailable.
A difference does not convert or re-seed the workspace. Legacy records without a sharing field keep `PRIVATE`.
The `seed` observation contains the [creation receipt](/reference/lifecycles#seed-outcomes), or an unavailable reason when the receipt cannot be admitted.
An unavailable receipt does not prove that seeding was not requested.

### Inspect or edit workspace settings

Use `show` to see the resolved configuration and the exact workspace file.
Use `explain` to see one setting and its source.

```shell
kast config show --workspace . --json
kast config explain KAST_WORKSPACE_DEPENDENCY_SHARING --workspace . --json
```

To save the shared policy for this workspace, use `set`.
To remove the workspace override, use `unset`.

```shell
kast config set KAST_WORKSPACE_DEPENDENCY_SHARING SHARED --workspace . --json
kast config unset KAST_WORKSPACE_DEPENDENCY_SHARING --workspace . --json
```

Each edit reports the resolved setting after Kast reads the file again.
The `DEFAULT` source names the policy for a new workspace.
For an existing workspace, `workspaceAccess` reports the recorded policy or the conflict that blocks reuse.
This comparison reads the workspace record without a Host.

## 2. Update

Save work in your agent before changing the installation. Preview selection, then apply it:

```shell
kast versions
kast upgrade --channel preview --dry-run
kast upgrade --channel preview --json
```

Use `stable` for stable builds.
An [exact version or commit](/reference/installation#pin-a-published-build) creates a pin.
An unqualified upgrade follows the recorded channel, but rejects a pin with `PINNED_BUILD`.

```shell
kast upgrade --repair --json
```

Repair selects the exact installed product. It does not resolve a newer channel head or replace only one component.
The installer composes immutable vendor bytes with exact components and uses the existing replacement journal.
Running owned work can end during replacement. A subsequent explicit request prepares the selected workspace generation.

## 3. Read the result

Keep the structured result, its failure code, and any recovery evidence.
Progress belongs on stderr; `--json` selects structured stdout.
A completed installation is not a claim that a workspace imported successfully or that a query completed.
Read `kast status --all --json`, then run one useful query in the intended workspace.

After an upgrade, [refresh each exported skill](/reference/integrations#refresh-the-skill-after-an-upgrade) and start a fresh agent session.
Do not replay an interrupted source change: inspect source and its [change receipt](/reference/change#read-the-receipt) first.

## 4. Resolve unfinished recovery

Use this after a recovery-required result or a nonempty `unresolvedTransaction` observation.

1. Keep the failure output and the selected product identity.
2. Correct the reported permission, ownership, or storage problem.
3. Repeat the management operation and inspect its result before another selection.

Recovery uses the existing transaction record to finish or undo the selected composition.
Unknown or damaged records fail closed. Do not delete journals or mix component archives to bypass admission.
Restored files do not prove that a Host runs again. Status and a useful query establish separate facts.

## Stop workspace Hosts

```shell
kast stop --json
kast stop --workspace /absolute/project/path --json
kast stop --all --json
```

Stop is temporary and scoped. The next explicit semantic request can restart the Host.
Without an option, `kast stop` stops only the Host of the current workspace; `--all` stops every recorded workspace Host.
The result names each stopped workspace, so a broad stop shows which Hosts must start again.
There is no persistent disable or resume command. A passive hook does not restart it.
Stopping Kast does not authorize termination of unrelated IDEA or Gradle processes.
An active lease can reject a stop as busy; preserve the result and retry only after the active work settles.

## State for removed workspaces

Request admission and upgrade retirement can reclaim private state for a workspace root that no longer exists.
Cleanup requires the exact retired Host generation, no active query lease, and settled `.kast` evidence.
It does not delete a repository or an external Gradle home.
An interrupted deletion keeps an exterior `.removing-ID.json` receipt for recovery. Do not remove that receipt manually.
These are source-level rules; native cleanup qualification remains pending.

<span id="uninstall" />

## Remove Kast

```shell
kast uninstall
```

The removal contract covers owned installation bytes and workspace state after process retirement.
Repositories, external Gradle homes, and agent configuration remain outside that scope.
To disconnect an agent, [remove the plugin](/reference/integrations#remove-the-plugin) and any exported skill before you uninstall.
Uninstall also removes the fixed Kast-owned `kast-workspaces/shared/gradle` cache, without following links to external targets.
Foreign siblings, foreign owners, or `.kast` recovery evidence prevent that cleanup.
Removing one workspace does not remove the shared cache.
If ownership or retirement cannot be proved, keep the recovery output instead of deleting paths manually.
Native removal acceptance remains part of the qualification work; this guide is not evidence that it passed.

## Reset a damaged installation

Use `kast reset` when `kast uninstall` or a repair fails. It reads no installation record and starts no Java.

1. Save the work in your agents.
2. Examine what Kast will stop and delete:

   ```shell
   kast reset
   ```

3. Run the reset from a terminal that Kast did not start:

   ```shell
   kast reset --yes
   ```

4. Run the installation command that the reset prints.

The reset stops the Kast service jobs, then the processes whose executable is in the installation.
It deletes the management root, the workspace and runtime stores, the login agents, the `/tmp` entries, and the `kast` command that Kast wrote.
It does not follow links, and it skips and lists each entry that is not a Kast entry.
The reset does not stop a Gradle daemon that uses your own Java.

Your repositories, external Gradle homes, agent configuration, and `~/.kast` stay in place.
Before it deletes a file, the reset copies the client configuration and the change evidence of each workspace.
The copy is in `~/.local/share/kast-reset-backup-TIME`. If the copy fails, the reset deletes nothing.
The change evidence can hold the original source of an unsettled change. A new installation does not read it.

Each failure prints a code and its cause. `HOME_REJECTED`, `ROOT_REJECTED`, `STOP_REJECTED`, and `BACKUP_REJECTED` delete nothing.
After `RESET_INCOMPLETE` or an interruption, correct what the output lists, then repeat `kast reset --yes`.
The reset deletes the `kast` command last.

## Change agents

Run `kast agent remove` for the old agent and `kast agent install` for the new one. [Connect your agent](/reference/integrations) describes both.
