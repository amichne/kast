This page describes compatibility that Kast itself owns. Release automation does
not attempt to infer compatibility by replaying previous binaries or comparing a
separate compatibility snapshot.

## Stable in 1.x

Within one major version, supported callers should be able to rely on:

- canonical operation IDs and the meaning of complete, qualified, and rejected outcomes;
- documented CLI commands, option spellings, exit behavior, and output channels;
- typed selector, continuation, plan, and generation semantics;
- supported configuration keys and explicit Gradle import inputs; and
- installer replacement, rollback, and uninstall behavior described below.

A source or semantic-generation change may invalidate selectors, continuations,
and plans. Compatibility does not authorize reinterpretation of stale identity;
the correct behavior is a typed stale or rejected outcome followed by fresh
resolution.

Semantic operations emit one final JSON document on stdout, including semantic
rejection. Boundary rejection uses stderr and a nonzero exit code. Terminal
startup progress remains stderr output so redirected stdout retains the machine
document.

## Versioned JSON shapes

Requests, outcomes, selectors, continuations, generations, plans, receipts, and
private state codecs have explicit version or identity boundaries. Changes to a
closed public shape require deliberate versioning; callers are not expected to
guess whether an unknown field or token is safe.

The source of truth is the typed protocol and generated CLI schema for the exact
installed version. There is no independent release-comparison artifact that can
override those authorities.

## Preview and supported hosts

Codex App Server integration is a decoupled, read-only preview while its upstream
protocol remains experimental. Its availability is not required for semantic
CLI use. Exact installed schemas and approval policies still fail closed.

Linux, Intel macOS, additional languages, and unsupported IntelliJ platform lines
are not promised. The supported host remains Apple Silicon macOS with the
documented IntelliJ release line and admitted JBR.

Hosted mutation supports only `add-declaration`. Other command grammar names do
not establish hosted implementation support.

## Upgrade and recovery

The installer validates the matched control and semantic-runtime assets before
replacing managed links. Activation replaces installer-owned links and verifies
the public command. A catchable failure or signal restores the previous
activation and literal configuration.

Ordinary upgrades preserve repository source and non-owned host state. Kast-owned
runtime stores and caches may be replaced or rebuilt when their identity is no
longer admissible. `kast start --cache rebuild` explicitly rebuilds disposable
cache state.

`uninstall --installation-only` removes the selected installation and its owned
runtime/configuration state. Ordinary `uninstall` also cleans historical
Kast-owned locations. Neither mode is authority to delete unrelated JetBrains or
repository state.

Installer behavior is exercised by `packaging/test-installer.sh`. Semantic
correctness, selector lifetime, and persisted-state behavior belong to their
owning Kotlin tests rather than an end-to-end release rehearsal.

## Pin installer content and product together

Resolve a published release tag, then execute the installer from that same tag:

```shell
release_url="$(curl -fsSL -o /dev/null -w '%{url_effective}' https://github.com/amichne/kast/releases/latest)"
release_tag="${release_url##*/}"
curl -fsSL "https://raw.githubusercontent.com/amichne/kast/${release_tag}/install.sh" | bash -s -- --version "$release_tag"
```

For a pinned installation, use the same explicit release tag for both installer
source and `--version`. A candidate document does not establish that a future
release exists.
