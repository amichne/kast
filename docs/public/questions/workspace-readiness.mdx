A running process is not proof that the repository model and compiler evidence
are ready. Ask for workspace evidence before interpreting a later symbol
result.

```console
cd /path/to/kotlin-repository
kast workspace inspect
```

## The answer belongs to one exact root

Kast canonicalizes the working directory and associates the request with the
private sidecar Project for that exact root. Two checkouts of the same Git
repository are two workspace identities. A user's foreground IntelliJ window
does not select the workspace, and unsaved editor buffers are outside Kast's
on-disk authority.

This prevents an answer from silently borrowing indexes, Gradle ownership, or
source state from another checkout.

The admitted model may include a declared local source directory that does not
currently exist, such as an empty resources or generated-source root. Kast
preserves that IntelliJ-owned root identity without inventing source content;
topology enumeration simply has no candidates beneath it until it appears.
Invalid protocols, malformed paths, and roots outside the exact workspace are
still rejected.

## Read readiness as evidence

The result identifies `workspace.inspect` and the semantic generation that
produced its payload.

<Columns cols={3}>
  <Card title="Complete">
    The exact root has a published workspace model and satisfies the
    operation's full readiness contract.
  </Card>
  <Card title="Qualified">
    The returned workspace facts remain usable, and the response names the
    limitation that prevents a stronger claim.
  </Card>
  <Card title="Rejected">
    Kast could not establish the required workspace evidence. No workspace
    payload is presented as success.
  </Card>
</Columns>

<Note>
  `kast status` passively reports whether the exact sidecar is running and
  whether its private cache is fresh, seeded, refreshing, smart, or requires a
  rebuild. `kast workspace inspect` may start the sidecar and answers whether
  semantic workspace evidence is available. Keep those questions separate.
</Note>

## Carry the generation forward

Candidates and exact selectors are issued against a semantic generation. If
the workspace moves, Kast rejects stale proof instead of treating an old
identity as current.

Restarting the sidecar also advances the generation conservatively. Kast cannot
prove source content stayed unchanged while the Project was closed from the
bounded workspace model alone. Rebuild topology to verify and, when the exact
candidates match, rebind the durable snapshot to the new generation.

Once readiness is sufficient, [establish the exact declaration](/questions/declaration-identity)
needed by the next question.
