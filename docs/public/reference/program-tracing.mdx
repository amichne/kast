Kast can answer two questions: who calls this code, and where does this value go?
Each answer keeps source sites and exact compiler identities. The path also states which proof is still missing.

A trace can cross functions or show steps inside one body.
For a callback, the evidence connects the body to the code that supplies and invokes it.
These are source relationships. They do not show that a particular execution reached the code or that every branch can run.

For an introduction through ordinary Kotlin code, read [Follow a value](/explanation/value-journey).
This reference defines the supported routes and their limits.

## Three tracing contracts

| Question | Contract | Evidence |
| --- | --- | --- |
| Which declarations connect to this symbol? | `EXPAND_RELATION`, `WALK`, or `TRACE` | References, calls, implementations, and overrides. The depth states how far the query goes. |
| How does this callback reach a call? | Callback observations in relationship reads | Who supplies it, which formal accepts it, and which body calls it. Aliases and forwarding connect those sites. |
| Where does this producer value travel? | `IMPACT` with `KOTLIN_FORWARD_V1` | Value paths, representation models, and destination sites. Terminals show where paths stop. Obligations state the proof still needed. |

These contracts share exact identities and source state. Each kind of edge states a different fact. A reference count cannot stand for a call count.

## Inside a function body

This source illustrates a callback route. It does not record a Kast response.

```kotlin
fun submit(block: () -> Unit) {
    val action = block
    forward(action)
}

fun forward(next: () -> Unit) {
    next()
}

fun checkout() {
    submit { charge() }
}
```

The compiler maps the supplied lambda to `submit.block`. The alias through `action` keeps that value. Its binding cannot change.

A *formal* is the parameter in the called function's declaration, here `block` or `next`.
Forwarding evidence connects `submit.block` to `forward.next`. The invocation `next()` belongs to `forward`.
The call to `charge()` belongs to the lambda body, even though that body appears inside `checkout`.

An admitted graph keeps proof for each hop. Unsupported transfers prevent a complete graph. So does an incomplete scan.

`checkout` supplies the lambda. That fact alone does not make it a direct named caller of the calls inside the lambda.

## Ownership and execution

Kast keeps five roles distinct:

- The named lexical container holds the source text, here `checkout`.
- The anonymous body contains its calls, here the lambda with `charge()`.
- The supplier passes the callback, here the `submit` call in `checkout`.
- The formal accepts it, here `submit.block`.
- The actual call owner contains the invocation, here `forward` with `next()`.

An unused default keeps its formal and expression. Kast does not invent a call. A nested body needs proof for its own invocation route.

Kast connects anonymous owners through exact supplier bindings and source summaries. It also uses direct calls and admitted library contracts. Each owner keeps its own proof. Lexical containment alone does not complete a route.

Reviewed calls-in-place contracts keep their declared call kind. Missing effects or effects that conflict cannot become `UNKNOWN`. That value cannot stand in for missing proof.

### Library calls need their own evidence

The `inline` modifier alone does not prove a callback route. Standard-library `with`, `apply`, and `let` declare `callsInPlace` effects.
Collection `map` and `forEach` do not declare those effects. Their inline modifier supplies no such proof. Missing dependency effects remain explicit proof gaps.

The reviewed `kotlin.lazy` model records the initializer supplied for later use. It does not prove that the property was read or that the initializer ran.

[Callback evidence](/reference/callbacks) describes these mechanisms. [Callback observation fields](/reference/callback-observations) defines their encoded variants.

## Producer values and representations

`IMPACT` starts from exact producer calls. Native reads prove source identity and supported Kotlin transfers.

Here, a producer is the selected constructor or function call whose result the investigation tracks.

Plain request and response paths trace constructor results, arguments, and receivers. They also trace proven immutable field storage and reads. Returns connect to the matching call. Supported nested calls and named locals keep that route. Different fields keep separate provenance. So do separate calls to the same mapper.

Interface calls can enter eligible source implementations within the declared domain. Each alternative keeps proof of its implementation and source owner. A complete static target set does not show which target ran.

An opaque call needs proof to connect a request argument to its response. Source evidence or a reviewed model must supply that proof.

Supplied reviewed models define how values change form. They also define how modeled callables behave. Each path records where it used a model. It keeps the native evidence too.

### Branches and fields keep separate proof

When a try or catch body completes normally, its final value can supply the try expression. Each catch alternative keeps its own producer identity.

Throws do not supply a normal result. Transfers across `finally` keep `FINALLY_UNSUPPORTED`. Kast does not prove that effect.

These transfers do not prove payload flow through containers. They do not prove subtype or non-null branch conditions. They also do not select collection elements. They supply no automatic models for logs, headers, or errors.

Field transfers need storage proof from the compiler. Other property access keeps its proof obligations. Unsupported evidence still prevents strict completion.

The retained witness lists producers, models, and native reads. It lists read rejections and findings. It keeps the record for each requested site. A site identity alone cannot prove a producer relationship.

[Query forms](/reference/api#investigate-value-impact) defines inputs and witness sections.

## Values through invoked callbacks

Supported immutable captures keep their exact binding. They also keep their anonymous owner. A captured argument remains distinct from a captured receiver. It also differs from the wrapper's receiver. A transfer that depends on invocation needs an admitted callback route. Lexical containment does not prove that route.

A callback result can enter the exact formal invocation. It can then return through the matching wrapper call. Each `CALLBACK_RETURN` keeps the supplier occurrence and invocation owner. It also keeps the source-call frame. Separate wrapper calls keep separate result identities.

### A callback result can be discarded

A wrapper can discard the result and return a constant. That constant has no transfer from the discarded result.

Unit coercion discards the expression's value. It does not return that value. Results of type `Unit?` remain values, not Unit coercion.

Immutable constructor fields and normal try branches keep this result provenance. A successful `Attempt.Value.value` path supplies no value to the exceptional `Attempt.Failure` branch. This does not prove that the code ran. It also does not connect a decoder's argument to its result.

### Unsupported invocation owners remain explicit

Value flow needs source proof for supply and invocation. Both must connect to the named root. Each anonymous body needs one invocation context. Formal invocations need named owners.

An invocation inside an anonymous owner remains unsupported. A named owner for another invocation does not remove that limit. The limit does not exclude anonymous callback suppliers.

Mutable captures keep explicit obligations. So do captures between distinct anonymous owners, unsupported routes, and unresolved owners. A returned callback can remain uncalled. That callback gains no value or result path that depends on invocation. Parameter declarations cannot seed public `IMPACT` queries.

## Completion and limits

Every public `RUN` uses `COMPILER_RESOLVED_STATIC_V1` with `COMPLETE_ONLY`. To complete, a run must finish its work and meet its proof rules.

`TRACE` from source symbols treats source completeness and callback execution as separate facts. Proven nested routes compose without a nesting gap. Unproved owner routes remain explicit gaps under `SOURCE_RELATIONSHIPS`. Missing library effects remain gaps too. Lexical containment or supply does not prove an invocation.

Explicit `CALLERS` expansion still needs a complete graph of callback invocations. A source `TRACE` can therefore complete while `CALLERS` rejects a missing dependency effect.
Source relationships and proved invocation routes answer different questions.

Both interpretations reject unresolved source identity or missing result membership. They also reject exhausted grants. A rejection keeps proved evidence when retention admits it. [Results](/reference/responses#run-completion) defines the rule for composed queries.

The model proves source relationships through the compiler. It does not prove that code ran, that a branch can run, or how often code runs. It does not prove project behavior after an edit.

## Runner-controlled execution

Public `RUN` defaults to `RUNNER_CONTROLLED`. This mode adds no implicit semantic deadline or work quota. It also adds no internal byte or result quota.
An explicit `maxElapsedMs` sets a timeout. The timeout includes model capture. Omission adds no semantic deadline.
Caller cancellation or a disconnected caller stops the operation.

```json
{
  "request": {
    "type": "RUN",
    "executionMode": "RUNNER_CONTROLLED",
    "source": {
      "type": "SEARCH_DECLARATIONS",
      "declarationName": "confirmReferenceTarget",
      "declarationKinds": ["FUNCTION"],
      "scope": {
        "type": "DIRECTORY",
        "relativeDirectoryPath": "relation/intellij/src/main",
        "sourceSetNames": ["main"]
      }
    },
    "steps": [{
      "type": "WALK",
      "relation": "CALLERS",
      "expansionScope": {
        "type": "SOURCE_DOMAIN",
        "sourceSets": ["main"],
        "sourcePolicy": "PRODUCTION_ONLY",
        "generatedSources": "EXCLUDE"
      }
    }],
    "terminalStep": {
      "type": "EMIT",
      "output": {"type": "SYMBOLS", "fields": ["NAME", "LOCATION", "SIGNATURE"]}
    },
    "retention": "RETAIN",
    "executionBudget": {"maxResults": 20, "maxReturnedBytes": 100000}
  }
}
```

In this mode, `maxResults` and `maxReturnedBytes` control output pages.
Explicit `maxWorkUnits` conflicts with the mode and rejects the request.
Preparation and transport frames keep their existing limits.
A runner can set its own timeout. That deadline limits the caller lifetime.

The example separates discovery scope from expansion scope. Discovery uses `scope.sourceSetNames` and `relativeDirectoryPath`. Expansion uses `expansionScope.sourceSets` and optional `directory`.
The seed's directory does not restrict later destinations. `WORKSPACE` expansion can include test sources, even when discovery selects `main`.
For production-only relationships, use `SOURCE_DOMAIN` with exact imported source-set names.
Set `sourcePolicy: "PRODUCTION_ONLY"`. Choose an explicit generated-source policy, as shown.
These constraints apply before native reads collect results. A later row filter cannot replace them.

Completion still needs exhaustive compiler proof.
Source changes, unsupported effects, and invalid continuations still reject the operation.
`RESUME` presents produced output only.
After source changes, a fresh `RUN` can get fresh authority for earlier exact references. The compiler must prove their current identity.
This does not refresh `READ_SOURCE` snapshots or immutable retained results.
This mode still limits each output page. It does not extend the retention TTL of external handles.
