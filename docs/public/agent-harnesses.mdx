Kast ships a turnkey Codex integration. Other agent hosts can integrate Kast by
consuming the exact installed server projection. That projection is the contract;
copied command tables or handwritten tool definitions are not.

## Prefer the included Codex integration

From the Kotlin repository root, run:

```console
kast codex
```

The integration ensures a launchd-owned App Server at Codex's standard local
daemon socket, qualifies the installed Kast and Codex contracts, and registers
the configured tools. `kast codex desktop` launches Desktop against that same
socket without substituting its Codex executable.

## Consume the installed projection

A custom harness has one integration path:

<Steps>
  <Step title="Read the exact installed contract">
    Invoke `kast --schema` and read its `serverProjection`. Treat an absent,
    malformed, unsupported, or contradictory projection as startup failure.
  </Step>
  <Step title="Qualify the hosted bootstrap">
    Preserve the namespace, policy, tool order, names, descriptions, input and
    output schemas, effects, approval policies, loading hints, and execution
    budgets. Do not infer any of them from a version string.
  </Step>
  <Step title="Join tools to invocation bindings">
    Match `hostedBootstrap.tools` to `cliInvocations.operations` by tool name,
    then verify the canonical operation ID. Require a unique, complete match
    before advertising a tool.
  </Step>
  <Step title="Invoke from the repository root">
    Execute the declared argument vector without a shell. Send one tool-input
    JSON object on standard input and validate the result against the declared
    output schema.
  </Step>
</Steps>

The harness should requalify the installed projection when the provider starts.
If the executable or projection has changed, construct a new catalog instead of
reusing stale metadata.

## Make search the default

`search_classes`, `search_functions`, `search_declarations` and `check_diagnostics`
are eager. Prefer the specific search when its declaration kind is known; use
`query_symbols` for enumeration, returned references and ordered pipelines.

The advanced query, source, semantic, impact and change tools are deferred.
Direct `symbol_lookup` and `symbol_inspect` remain opt-in. Change planning does
not require approval; apply and recovery require approval of the exact stored
plan. Several tool names bind to `query.run`; join
installed CLI invocations by `toolName`, not just `operationId`. Projection 10
and CLI invocation version 3 require the matched installed contract.

The harness must also preserve returned references verbatim. It must not rebuild
selectors from names, file paths, or source text.

## Let operations own readiness

Do not expose lifecycle, index synchronization, topology preparation, status,
or broker administration as agent tools. Semantic reads use the existing saved, indexed IntelliJ project and reject an
unavailable host. Operations retain their own evidence and readiness boundaries.

This keeps the agent contract task-oriented and prevents a harness from creating
an invalid prerequisite sequence.

## Preserve the failure layers

There are two result layers:

- An outer `completed` result means the declared invocation ran and produced a
  schema-admitted semantic document.
- An outer `rejected` result carries a `diagnostic` for a process, runtime,
  protocol, or output-boundary failure.

Inside a completed invocation, the semantic document can still be `complete`,
`qualified`, or `rejected`. Keep its status, limitations, item failures, and
proof-carrying references available to the model. Never flatten a qualified or
rejected semantic outcome into ordinary success.

## Configure the App Server catalog

The installer writes App Server settings beside `KAST_ENABLE_LAUNCHD` in the
selected release's `config/environment` file. By default, the selected file is
available through `~/.local/share/kast/current/config/environment`. Disable the
integration without removing Kast with a process override:

```shell
KAST_ENABLE_APP_SERVER=0
```

Fresh installations materialize every saved-installation default in this file,
including `KAST_DEBUG=0`. Each App Server launch also atomically writes the full
resolved non-secret snapshot to the `launchEnvironment` path reported by
`kast app-server status`. Use `KAST_DEBUG=1` to stream bounded launch diagnostics
to stderr in addition to the persistent service log.

Set `KAST_APP_SERVER_TOOLS` to an exact, non-empty comma-separated subset of the
names in `kast --schema`. Process values override the saved file. Unknown,
duplicate, or empty names reject startup. The default value is:

```text
search_classes,search_functions,search_declarations,query_symbols,source_read,semantic_query,impact_analyze,check_diagnostics,change_plan,change_apply,change_recover
```

Change tools are deferred defaults. Tool selection does not grant live mutation
authority or bypass the separate approval required by apply and recovery.

## Use a stored change plan

See [Add a Kotlin declaration](/change) for the user workflow and recovery states.

The existing-IDE change path currently supports `AddDeclaration` in one existing,
authored Kotlin source file. Keep the saved project open in IntelliJ with the
matched Kast plugin. Missing hosts, unsupported intents and stale references
reject without starting an isolated workspace.

Enroll the local broker explicitly before applying or recovering a plan:

```console
kast ide trust-broker
```

This creates an Ed25519 key pair in `~/.kast/approval`, or preserves an existing
matching pair. The approval directory and keys are private to the local user.
Unsafe paths, incomplete keys and mismatched keys reject. Apply does not create
keys or enroll trust automatically.

1. Use a Kast search and pass its returned `symbol_ref` unchanged to
   `change_plan` as the exact target. Use the installed tool schema for the
   `add-declaration` request.
2. Keep the returned immutable plan identity and review its file preview.
   Planning does not change source or grant write permission.
3. Invoke `change_apply` with that identity. The included Codex integration loads
   the stored preview, emits a separate native `fileChange` preview item, and
   requests approval from the current controller. The original dynamic-tool item
   keeps its identity and content. Decline, cancellation, lost control and expired
   approval reject before writing.
4. Preserve the complete semantic result. `Verified` includes a durable receipt;
   `AppliedUnverified` means the write occurred but verification or receipt
   persistence did not complete; `RecoveryRequired` retains an uncertain attempt.
   The latter two are qualified outcomes, not verified success.

Apply rechecks the plan's exact root, IDE owner, epoch, project model and saved
preimage at the write boundary. Repeating an already verified plan returns its
stored receipt without repeating the write. An interrupted attempt requires
recovery. `change_recover` requests a new exact-plan approval and uses durable
records plus a fresh source observation to establish the prior state or roll
back an exact matching postimage. Divergent or unavailable evidence remains
recovery-required.

A custom harness must provide the approval integration required by the installed
contract. A plan identity, catalog approval policy or ordinary CLI invocation
cannot substitute for controller approval.

For operational symptoms and safe status collection, see
[Troubleshooting](/troubleshooting).
