Use the exact repository or worktree you want to inspect. Kast prepares its IntelliJ project when a semantic request needs it; there is no separate workspace-open step.

## Check that the tools work

Ask your agent:

> Use Kast to find one Kotlin declaration in this repository. Show its name, kind, signature, source location, and coverage. If Kast is not ready or cannot prove a result, report the blocker rather than substituting a text search.

Success means an actual Kast query returns a declaration and its evidence. Seeing a registration in `kast status`, or seeing tool names in a catalog, is not the same check.

Then try [Find and trace code](/search). You ask the question; your agent chooses the query and passes the returned references to follow-up calls.

## A connection already exists

Reconnecting the same payload is safe. Kast preserves a conflicting registration by default. Inspect the reported conflict before explicitly replacing only that harness's Kast slot:

```shell
kast connect codex --force
# or: kast connect copilot --force
# or: kast connect pi --force
```

Forced connection verifies the bundled payload and captures the previous registration before replacement. A failed transaction attempts to restore the previous registration and receipt. If restoration fails, the error identifies the backup and recovery destination. Unrelated registrations stay in place.

## Disconnect or upgrade

```shell
kast disconnect copilot
```

Replace `copilot` with the harness you connected. This removes an owned registration; it is not a command to stop every existing agent session or IDEA process. Restart the affected harness so it stops using its loaded integration.

After `kast upgrade`, restart IDEA and your connected harnesses so they load the matched payload and rediscover its catalog.
