A Kast change is complete only when the strongest relevant executable evidence
supports it. The repository therefore verifies pure domain behavior, compiled
architecture, runtime integration, the installed product, semantic acceptance,
and documentation as distinct layers.

## Verification rings

Use the narrowest check that can disprove the change, then widen only as the
affected surface requires:

| Ring | Typical evidence | What it proves |
| --- | --- | --- |
| Focused | One module test or targeted test class | The next domain invariant or regression. |
| Owning module | Module `test` and `check` tasks | Compilation, tests, and module-local policy. |
| Architecture | `verifyKastArchitecture` | Admitted modules, dependencies, roles, and compiled effects. |
| Product assembly | `assembleSidecarRelease` and distribution checks | Control and sidecar artifacts are coherent and physically separated. |
| Installed product | Packaging shell and Python verification | The archive, installer, metadata, lifecycle, and passive commands work outside Gradle internals. |
| Enterprise | Staged product against the multi-module fixture | End-to-end semantic behavior, mutation, isolation, and performance bounds. |
| Documentation | Registry generation, LikeC4 check, docs contract, and `mint validate` | Published commands, claims, links, pages, and diagrams match their authorities. |

Running a broader ring does not make a missing narrow invariant precise. A
focused test explains the intended property; wider checks prove that the
property composes with the product.

## Installed product proof

The control command and private sidecar are built and verified as one matched
product. Verification checks metadata and SHA-256 records, archive safety,
runtime identity, required resources, control-versus-sidecar content
separation, relocatability, and lifecycle behavior.

Bare inspection is tested as passive: it must not
start the sidecar merely to report absence. Start, stop, bare inspection, cache reuse,
cache seeding, cache rebuild, and wrong-root behavior are exercised against a
staged installation, not inferred from unit tests.

Release assets also provide machine-readable CLI schema and module knowledge.
The latter binds a release version and Git revision to accepted architecture
evidence, canonical module policy, observed direct dependencies, and applicable
repository guidance. It is a transportable index into stronger authorities,
not a replacement for them.

## Enterprise acceptance

The enterprise fixture tests the staged product against a real multi-module
Gradle workspace.

Through the public command boundary, it checks:

- cross-module symbols and relationships;
- deterministic, bounded semantic output;
- topology, traversal, and generation transitions;
- mutation and recovery lifecycles; and
- measured performance ceilings.

This layer catches errors that an in-process test cannot represent: packaging
omissions, launcher environment mistakes, incompatible private plugin layout,
socket isolation, and failure to preserve identity across process boundaries.

## Release admission

Routine pull-request and main CI starts from a detached clean checkout of the
exact commit. Python contract tests run first.

The `productBuildGate` Gradle graph
then builds every module and verifies architecture and installed packaging;
`enterpriseAcceptance` runs one installed semantic journey. Installer recovery
and documentation retain their independent checks.

Routine CI does not build a
publishable release candidate or run the exhaustive topology and import cases.
The required check retains the name `Release gate` for branch-rule continuity.

For release qualification, manually dispatch the `CI` workflow on `main`.
This runs the exhaustive `releaseSourceGate` graph, including topology declaration
bindings, installer recovery, and documentation, followed by exact-archive
installation, corruption, cold broker, and Gradle import proofs.

After that graph passes, the gate builds and installs the exact candidate
archives through `install.sh --assets-directory`. This uses the normal checksum,
archive-path, and manifest checks while avoiding a dependency on publication.

The installed journey runs with no Codex executable or `CODEX_HOME`, checks
semantic reads, restart continuity, verified mutation, and scoped uninstall
followed by reinstall. A separate cold read-only broker journey checks canonical
CLI equivalence, selector reuse, and the source companion presentation.

The cold harness persists bounded stage, process, and dispatcher observations
before failure. Reports retain finite rejection IDs, byte counts, and digests;
source payloads, selectors, paths, and arbitrary error text are excluded.
Cleanup cannot replace the original failure or turn a rejected receipt into success.

The candidate is installed directly. Installer fixture tests retain replacement,
corruption, and recovery coverage. This installed journey does not claim coverage
of upgrades from historical published versions.

Real relation and traversal continuations must resume successfully before
malformed and digest-tampered copies are rejected. Corrupting the selected cache
identity receipt must appear as a typed blocker in passive inspection. Exact receipt restoration must
recover inspection and a semantic read while preserving the repository.

The required installed import uses Gradle 9.4.1 and Java 25 through
`KAST_RELEASE_JDK_25`. It proves admitted environment inputs, explicit executable
lookup, and exclusion of an unselected secret-like variable. Other JVM
compatibility rules retain their unit tests without a full installed matrix.

The receipt binds the canonical cases in `benchmarks/gradle-import-acceptance.json`,
the executable acceptance script, and each JDK's release metadata. Successful
imports must use the isolated admitted Gradle home.

Command observations retain durations and evidence digests as the journey runs,
including finite failure causes if it stops early.

Resource observations sample only processes proven to own the selected IntelliJ
cache. Headless processes are located by the exact owned system argument and
checked again by PID; process command lines are never serialized.

They record RSS after
start, a semantic read and restart, then prove the owned runtime is absent after
stop. Apparent bytes cover the selected installation and runtime state without
following links.

The maximum observed RSS is a sampled maximum, not a continuous
peak. These measurements add no speculative resource threshold.

The resulting `kast-release-receipt-v<version>.json` binds the source revision,
canonical command digest, predecessor receipts, observed IDEA/JVM environment,
and archive digests. A checksum-pinned Syft scan inventories the two packaged
archives in `kast-sbom-v<version>.cdx.json`; its digest is a required predecessor.

The source predecessor records its archive output digests immediately after the
successful build. Installed and published bytes must match those outputs.

The packaged schema, command surface and persisted-state owners form
`kast-compatibility-v<version>.json`. Its comparison with the latest immutable
stable baseline is another required predecessor. Publication rechecks that
baseline before uploading a draft.

Publication requires both that receipt and a successful
`Release gate` check for the exact release SHA. A failed predecessor produces no
publishable receipt. Draft upload verification must preserve the admitted bytes
before the release can become public.

CI retains the candidate archives, checksums, receipts, SBOM, compatibility
snapshot, and reports for 90 days. Release admission requires the latest successful
`CI` manual-dispatch run on `main` for the exact SHA and the reviewed candidate version.
Missing or expired artifacts reject publication before toolchain setup.

The release workflow downloads that run's `release-candidate-<sha>` artifact,
verifies the receipt and all payload digests, attests the retained bytes, and
publishes them without rebuilding or repeating installed acceptance. Uploaded
draft bytes must still match the admitted receipt.

Advance the candidate version in source before manual qualification if a different release version
is needed.

Knowledge-authority checks rerun only `verifyKastArchitecture` and
`generateKastModuleKnowledge`; compilation prerequisites remain incremental.
The source gate does not perform an unconditional Gradle `clean`.

Run the same entry point from an isolated detached worktree:

```shell
bash .github/scripts/release/build-assets.sh \
  --version "$(cat distribution/release/candidate-version.txt)" --source-revision "$(git rev-parse HEAD)"
```

This command verifies a candidate; it does not publish a release. The version
must be the intended candidate version. Reports live under
`build/reports/release-gate/`, with the receipt beside the release archives.

CI reads its proposed version from `distribution/release/candidate-version.txt`.
Advance that reviewed version after a stable release; the compatibility gate
requires candidates to move forward from the published baseline.

## Reproduce CI locally

Routine CI needs macOS arm64, Python 3.12, and Java 25. From a detached clean
checkout, run:

```shell
export KAST_RELEASE_JDK_25="/path/to/jdk25"
python3 .github/scripts/ci/verify-checks.py
```

Exhaustive release qualification also needs Node 24, Mintlify CLI 4.2.841,
and authenticated `gh`. To retain an isolated worktree for that qualification:

```shell
export KAST_RELEASE_JDK_25="/path/to/jdk25"
bash .github/scripts/ci/reproduce.sh HEAD
```

The command creates a detached worktree for the committed revision and runs
`.github/scripts/ci/verify.sh`, the exhaustive gate used by manual CI dispatch.
It retains the worktree, log, candidate archives, and reports for inspection.
Uncommitted edits are not included. Dependency caches remain reusable.

The default IDEA runtime comes from the repository's pinned distribution, so
an IDE installed on the developer's machine cannot silently change the test.
## Release integrity

The wrapper distribution has a SHA-256 pin and URL validation. Gradle verifies
dependency artifacts and metadata against `gradle/verification-metadata.xml` in
strict mode. Release builds never regenerate those checksums automatically.

When changing dependencies, review the resolved coordinates and new checksums
against the expected repositories before committing the updated metadata. The
initial checksum set records reviewed downloaded bytes; it does not claim
upstream signature verification.

Check metadata coverage with an empty `GRADLE_USER_HOME` as well. Warm caches can
omit parent POMs, BOMs and module metadata that a fresh runner must resolve.

For an unlisted artifact, verify its exact coordinates and bytes against the
publishing repository and available published checksum before adding its SHA-256
pin. Preserve strict verification throughout this check.

Actions are pinned to full commit identities. The release workflow attests the
verified candidate files before publication. The SBOM describes bundled
components; the user-supplied IntelliJ distribution and JBR remain external host
dependencies. Security-reporting instructions are in the repository's `SECURITY.md`.

## Keep this specification authenticated

The documentation workflow forms its own proof chain:

```text
CanonicalOperation and command graph
  -> generated operation registry
  -> generated CLI reference

LikeC4 source and locked generator
  -> provenance-checked web-component bundle
  -> embedded technical views

Source authorities and Mintlify navigation
  -> docs/test_public_docs.py
  -> mint validate
```

When mechanics change, update the source contract first. Regenerate derived
artifacts with their owning task, update only the affected explanation, and add
or strengthen a docs assertion for any claim whose drift would mislead a
maintainer. Do not patch generated CLI or LikeC4 output by hand.

Every public page also declares bounded `code_sources` in its OKF header. Ask
which pages cite a changed authority before editing prose:

```shell
python3 docs/test_public_docs.py --impact path/to/changed-source.kt
```

## Contributor path

<Steps>
  <Step title="Name the invariant and owner">
    Identify the boundary input, trusted domain value, finite failure set,
    package or module owner, and executable proof that can fail before the fix.
  </Step>
  <Step title="Orient through contracts">
    Start at the canonical operation or domain contract, then follow service,
    adapter, composition, wire, and CLI projections only as far as the change
    requires.
  </Step>
  <Step title="Prove the narrow behavior">
    Add the smallest public-behavior test, observe the intended failure, and
    implement the narrowest typed transition that makes it pass.
  </Step>
  <Step title="Widen verification">
    Run owning-module and architecture checks, then product, enterprise, or
    documentation rings when the changed surface crosses those boundaries.
  </Step>
  <Step title="Leave an authority trail">
    Keep durable rationale in contracts, tests, architecture policy, or this
    specification. Generated artifacts must retain their provenance.
  </Step>
</Steps>
