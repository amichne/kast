A custom harness must load its contract from the Kast executable it invokes.

<Note>
  For the included integration, run `kast codex` from the repository root and
  continue with [Search declarations](/search).
</Note>

## Bind the catalog once at startup

<Steps>
  <Step title="Admit the installed projection">
    Run `kast --schema` and consume `serverProjection`.

    - Require server projection version 13.
    - Require CLI invocation version 3.
    - Reject missing, malformed, unsupported, or contradictory data.
    - Validate the complete contract instead of trusting version numbers alone.
  </Step>
  <Step title="Join by tool name">
    Match `hostedBootstrap.tools` with `cliInvocations.operations` by `toolName`.

    Require exactly one binding per tool and verify its canonical operation ID.

    Multiple search tools share `query.run`, so operation identity is insufficient.
  </Step>
  <Step title="Register the complete tool definition">
    Preserve every declared field:

    - namespace, policy, order, name, and description
    - input and output schemas
    - effect and approval policy
    - deferred-loading hint and execution budget

    Invoke the executable with the admitted argument vector and repository root.

    Never interpolate tool input into a shell command.
  </Step>
  <Step title="Validate and return the whole result">
    Send one JSON input on stdin.

    Admit output against the selected tool's schema and preserve both result layers.

    Return semantic status, payload, qualification, item failures, and unchanged references.

    [Read a response](/reference/responses) describes the dispatch rules.
  </Step>
</Steps>

Requalify whenever the provider starts or the executable changes.

## Choose what the agent sees

| Availability | Tools | Why |
| --- | --- | --- |
| Eager defaults | `search_classes`, `search_functions`, `search_declarations`, `check_diagnostics` | Directly express common reader intent |
| Deferred defaults | `query_symbols`, `source_read`, `read_relations`, `traverse_relations` | Add pipelines, source, relations, and traversal when needed |
| Deferred changes | `change_plan`, `change_apply`, `change_recover` | Keep planning and approval attached to stored changes |
| Explicit opt-in | `symbol_lookup`, `symbol_inspect` | Expose candidate discovery and refinement when required |

Keep these operations outside the agent tool catalog:

- lifecycle and synchronization
- topology setup and status
- broker administration

Reads use the saved IDEA project and return a typed blocker when evidence is unavailable.

## Preserve approval as an operation

Approval follows the operation:

| Operation | Approval |
| --- | --- |
| `change_plan` | None |
| `change_apply` | Exact stored plan |
| `change_recover` | Exact stored plan, approved separately |

A plan ID or `EXPLICIT` catalog field is not approval.

The included integration shows the stored preview and asks the current controller.

Decline, cancellation, lost control, and expiration reject before writing.

A custom harness must implement the installed approval contract.

Follow [Change source](/change) for trust, plan lifetime, apply states, and recovery.

Never render `applied_unverified` or `recovery_required` as verified success.

## Configuration and migration

<AccordionGroup>
  <Accordion title="Use the complete suite">
    Every installation exposes the complete catalog from `kast --schema`, including
    raw symbol tools and workspace lifecycle operations. Mutation approval remains required.

    `KAST_APP_SERVER_TOOLS` and `KAST_ENABLE_APP_SERVER` are retired. Remove them
    from saved configuration and the launch environment; they reject startup.
    Use `kast app-server stop` or `disable` for explicit service lifecycle control.
  </Accordion>
  <Accordion title="Find the configuration used by a launch">
    The installer saves App Server settings in the selected release's
    `config/environment`.

    The current release is normally available at
    `~/.local/share/kast/current/config/environment`.

    - Process values override saved values.
    - Fresh installations materialize defaults such as `KAST_DEBUG=0`.
    - `kast app-server status` reports configuration and service-log paths.
    - `KAST_DEBUG=1` also streams bounded launch diagnostics to stderr.
  </Accordion>
  <Accordion title="Migrate an older query integration">
    Recreate persisted catalogs with the matched executable and broker.

    - `kast.query` is not an alias in the new agent catalog.
    - `kast.diagnostic_check` is not an alias in the new agent catalog.
    - Use the intent tools for new registrations.
    - Treat legacy `kast query run` as a separate CLI grammar.
  </Accordion>
</AccordionGroup>

## Relation tool name compatibility

Version 11 advertises the preferred relation tool names:

| Operation | Preferred name | `0.40.x` alias |
| --- | --- | --- |
| `relation.read` | `read_relations` | `semantic_query` |
| `traversal.run` | `traverse_relations` | `impact_analyze` |

- Alias removal occurs no earlier than `0.41.0`.
- Saved selections normalize to the preferred names.
- Selecting both names for one operation rejects as a duplicate.
- An alias cannot enable an omitted tool.
- Older persisted catalogs must requalify before dispatch.
- Aliases do not bypass catalog digest binding.

The CLI commands remain `kast relation read` and `kast traversal run`.
