A running process alone is not proof that the repository model and compiler
evidence are ready. `start` is the sole admission flow and completes only after
the exact-root runtime is ready for semantic requests.

```console
cd /path/to/kotlin-repository
kast start
```

## The answer belongs to one exact root

Kast canonicalizes the working directory and associates the request with the
private sidecar Project for that exact root. Two checkouts of the same Git
repository are two workspace identities. A user's foreground IntelliJ window
does not select the workspace, and unsaved editor buffers are outside Kast's
on-disk authority.

This prevents an answer from silently borrowing indexes, Gradle ownership, or
source state from another checkout.

The admitted model may include a declared source directory that does not yet
exist, such as an empty resources or generated-source root.

- Kast preserves the IntelliJ-owned root identity.
- It invents no source content.
- Topology has no candidates there until the directory appears.
- Invalid protocols, malformed paths, and outside-workspace roots are rejected.

## Read readiness as evidence

The lifecycle route returns complete evidence only after the exact-root runtime
has reconciled its owned endpoint and admitted the workspace.

```json
{
  "command": "start",
  "status": "complete",
  "runtime": "running",
  "root": "/path/to/kotlin-repository",
  "runtimeId": "kast-sidecar",
  "removed": []
}
```

The root and running state are established. Later operations can now issue
generation-bound selectors and snapshots. Admission failures remain typed
lifecycle-boundary rejections rather than semantic-operation results.

<Note>
  The lifecycle document does not include a semantic `generation` field. Use
  `start` to establish readiness, then preserve the generation-bound selectors,
  snapshots, plans, and receipts returned by semantic operations.
</Note>

<Note>
  `kast status` passively reports whether the exact sidecar is running and
  whether its private cache is fresh, seeded, refreshing, smart, or requires a
  rebuild. It never starts or repairs the runtime. Use `kast start --cache
  reuse|seed|rebuild` for admission and cache policy.
</Note>

## Observe cold startup

On a terminal, `kast start` writes bounded progress to stderr as it discovers
runtime, selects the Gradle JVM, imports the Gradle model, indexes, captures the
workspace model, assembles runtime, and activates transport. Each update names
the phase, elapsed seconds, and completed phases.

Counts represent completed
phases; they do not estimate the percentage of Gradle or indexing work remaining.
An unchanged phase emits a heartbeat at most once every five seconds, with at
most 256 progress lines per invocation.

Machine output keeps the existing channel contract: a successful start emits
one final JSON document on stdout; boundary rejection emits one JSON document
on stderr. Progress is disabled when no terminal is attached.

Run `kast status` from another terminal during startup. Its `bootstrap` field
reports the last recorded phase and exact `attemptId` from the identified cache,
without starting, repairing, or waiting for the sidecar.

The separate `runtime`
field reports endpoint liveness; recorded bootstrap evidence alone does not
prove that its process is still alive. Missing or invalid bootstrap evidence is
reported as `unavailable` or `invalid`.

A child-reported startup rejection retains its attempt identity, failed phase,
finite cause, and one corrective action in `bootstrap`. For example, JVM
selection failures retain the wrapper version, required Java range, candidate
identities, selection authority, and the observed correction when available.

Startup logs
retain bounded phase and outcome events, never source text, credentials, or
unbounded exception messages.

## Carry the generation forward

Candidates and exact selectors are issued against a semantic generation. If
the workspace moves, Kast rejects stale proof instead of treating an old
identity as current.

Restarting the sidecar also advances the internal generation conservatively.
Kast cannot prove source content stayed unchanged while the Project was closed
from the bounded workspace model alone. Rebuild topology to verify and, when
the exact candidates match, rebind the durable snapshot to the new generation.

Once readiness is sufficient, [establish the exact declaration](/questions/declaration-identity)
needed by the next question.
