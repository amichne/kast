This is Kast's **Backing specification** for people who need to develop,
review, operate, or maintain the implementation. It answers "how does this
work?" at the level where a repository root becomes a runtime capability, an
operation becomes a typed dispatch path, and compiler observations become
host-neutral evidence.

<Note>
  This is a descriptive map, not an alternative authority. Kotlin types,
  generated schemas and registries, architecture policy, executable tests, and
  the released product remain stronger evidence. When this prose and a
  mechanically verified source disagree, the source wins and this page must be
  repaired.
</Note>

The [usage guides](/questions/workspace-readiness) begin with a question a
caller wants to answer. This specification begins with the boundary that must
prove the answer. It is intentionally selective: it explains the load-bearing
mechanics and gives maintainers a trustworthy route into the code, rather than
duplicating every type or function.

## How to read this specification

Follow information in the same direction that Kast does:

<Steps>
  <Step title="Locate the weak boundary">
    CLI arguments, filesystem paths, JSON documents, installed IDE metadata,
    and live compiler objects enter as untrusted observations.
  </Step>
  <Step title="Find the refinement">
    A parser, private constructor, sealed result, registry constructor, or
    admission service either proves a stronger value or returns finite failure
    data.
  </Step>
  <Step title="Preserve the proof">
    Exact root, operation, generation, scope, bounds, and limitations remain
    attached as information moves through the system.
  </Step>
  <Step title="Identify the effect owner">
    Process control, IntelliJ access, source writes, SQLite, time, and telemetry
    belong to explicit adapters. The core does not acquire these capabilities
    accidentally.
  </Step>
</Steps>

## One request, seven trust transitions

</Frame>

| Transition | What becomes stronger |
| --- | --- |
| Command parsing | Raw arguments become one recognized CLI action and canonical operation identity. |
| Runtime admission | A starting path becomes one canonical root and one compatible, exact-root sidecar endpoint. |
| Frame admission | A bounded string becomes a structurally valid request envelope. |
| Route selection | A permanent operation ID selects exactly one generated decoder and typed handler. |
| Semantic execution | A generation-bound request receives request-local IntelliJ, PSI, index, and K2 authority. |
| Detachment | Live compiler objects become stable domain identities, facts, coverage, and limitations. |
| Outcome projection | The caller receives one complete, qualified, or rejected host-neutral document. |

No later transition is allowed to erase an earlier identity. A transport reply
cannot manufacture semantic success, and a current compiler observation cannot
retroactively make a stale generation current.
