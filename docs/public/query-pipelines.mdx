`kast.query_symbols` applies an ordered pipeline to Kotlin declarations.

This example filters public functions before finding their callers:

```json
{
  "request": {
    "action": "run",
    "source": {
      "type": "all_declarations",
      "declaration_kinds": ["function"],
      "scope": null
    },
    "steps": [
      {"type":"where","predicate":{"type":"visibility","values":["public"]}},
      {"type":"expand_relation","relation":"callers"}
    ],
    "output": {"type":"symbols","fields":["name","location","signature"]}
  }
}
```

## Build the pipeline

| Part | Supported values |
| --- | --- |
| Sources | `search_declarations`, `all_declarations`, `symbol_refs`, `result` |
| Steps | `where`, `expand_relation`, `walk`, `concat`, `intersect`, `union`, `difference`, `distinct_symbols` |

Put the source and steps inside `request` with `action: "run"`. Choose an optional
typed `output` to present symbols, individual relation occurrences, or depth-bearing traversal records.
The other actions are `resume` and `read_result`; each accepts only its own fields.

Step order changes the result:

- Filter before expansion to find callers of public functions.
- Filter after expansion to keep only public callers.
- Expect discovery sources to preserve repeated rows in order after compiler refinement; add `distinct_symbols` where you want one row per identity.
- Add `distinct_symbols` to deduplicate downstream results.
- Concatenate exact references or a retained result at any point; later steps act on the combined stream.

Kast preserves every explicit step in order.

## Choose result presentation

| Input | Result |
| --- | --- |
| `request.steps: null` or `[]` | No transformations |
| `request.output: null` or omitted | Symbols with name and location |
| `request.output: {"type":"symbols","fields":[]}` | Mandatory identity and kind only |
| `request.output: {"type":"occurrences"}` | One row per relation occurrence, including repeated use sites |
| `request.output: {"type":"traversal_records"}` | One row per reached traversal record, including its depth and relation fact |
| Duplicate symbol projection fields | Rejected request |

## Reuse an exact symbol

Copy an exact symbol's `ref` verbatim into the `symbol_refs` source of a new run:

```json
{"request":{"action":"run","source":{"type":"symbol_refs","symbol_refs":["<returned exact ref>"]},"steps":null,"output":null}}
```

- Do not construct, shorten, or edit a reference.
- Expect the original owner to re-admit its workspace, lifetime, epoch, and scope.
- Add `expand_relation` and select `output: {"type":"occurrences"}` for use-site facts.
- Select symbol output for related declarations.

## Combine earlier query results

Run each input query with `"retention":"retain"`, then use their issued result references as inputs. For example, concatenate two retained results, explicitly remove duplicate identities, and select functions:

```json
{
  "request": {
    "action": "run",
    "source": {"type":"result","result":"<first retained result reference>"},
    "steps": [
      {"type":"concat","input":{"type":"result","result":"<second retained result reference>"}},
      {"type":"distinct_symbols"},
      {"type":"where","predicate":{"type":"primitive","field":"kind","operator":"equals","value":"function"}}
    ],
    "output": {"type":"symbols","fields":["name","location"]}
  }
}
```

`concat` retains stream order and multiplicity. Its `input` can also be
`{"type":"symbol_refs","symbol_refs":["<issued exact ref>"]}`. Every exact
reference is revalidated in the current read authority under the same query
budget; an invalid reference reports its step and position. `distinct_symbols`
removes duplicates by canonical semantic identity at that point only. It does
not compare names or opaque token spellings.

`where` accepts one structured predicate. A `visibility` predicate has a
nonempty, unique list of compiler-established `values`: `public`, `protected`,
`internal`, `private`, or `local`. A `primitive` predicate chooses `name`,
`kind`, or `file`; an operator `equals`, `not_equals`, `starts_with`, or
`ends_with`; and a nonblank literal of at most 512 characters. For example:

```json
{"type":"where","predicate":{"type":"primitive","field":"file","operator":"ends_with","value":".kt"}}
```

The predicate reads the compiler-grounded symbol description without starting
a source read. `file` is the symbol's stable file path or URL; `kind` uses
`class`, `constructor`, `function`, `property`, or `type_alias`. Unknown fields,
operators, and predicate variants reject at public admission.

For set composition, use `intersect`, `union`, or `difference` with a retained
result as `right`:

```json
{"type":"intersect","right":{"type":"result","result":"<issued retained result reference>"}}
```

These steps compare canonical semantic identities. `intersect` retains matching
left rows and merges evidence from matching right rows. `union` keeps identities
from either side; `difference` keeps left identities absent on the right.
Set operations form sets at their stage, while `concat` preserves multiplicity.
Right-hand omissions and qualification remain visible. `difference` rejects an
incomplete right input because it cannot establish absence. Selecting fewer
than all rows on the right makes that input incomplete too.


## Retain and reuse a query result

Set `"retention":"retain"` on a run when later stages should use its rows.
The response's `retention` is `retained` with an issued `reference`,
`capacity_exceeded`, or `not_requested`. Capacity failure does not discard the
current query answer. A retained result is immutable, bounded, and tied to the
semantic basis that produced it. An empty retained result is a valid input.

Start the next run from the issued reference. A retained item also carries a
`row_id` when Kast issues a result reference. Pass `row_ids` with that owning
result reference to select specific rows; omit it or use null for all rows, or
use `[]` for an empty selection:

```json
{
  "request": {
    "action": "run",
    "source": {"type":"result","result":"<issued result reference>","row_ids":["<issued row_id from this result>"]},
    "steps": [{"type":"where","predicate":{"type":"visibility","values":["public"]}}],
    "output": {"type":"symbols","fields":["name","location"]}
  }
}
```

The next run keeps the retained result's qualification and omissions. A subset
also records that excluded rows were not examined. Known positive rows remain
usable; an incomplete input cannot prove absence. Copy result and row references
as issued. A row ID is bound to one retained result and is distinct from an
exact symbol `ref`.

To present saved symbol rows again without running query stages, use
`read_result`. It accepts symbol output only. To present relation occurrences,
start a new run from the retained result with occurrence output. The
`read_result` cursor starts at zero when omitted. The returned
`next_cursor` identifies the next presentation page when present:

```json
{"request":{"action":"read_result","result":"<issued result reference>","cursor":0,"output":{"type":"symbols","fields":["name","location"]}}}
```

## Continue an interrupted pipeline

A qualified response may include an execution `continuation`. Resume by
sending only that token and, optionally, a new `execution_budget`:

```json
{"request":{"action":"resume","continuation":"<issued execution continuation>"}}
```

Append each returned page in order. The token restores the original source,
steps, output choice, and retention request; resending those fields is
rejected. `continuation` resumes semantic execution. `next_cursor` only pages
through one separately supplied retained result.

The checkpoint retains:

- unfinished relation expansion
- unfinished walk frontier and its domain continuation
- pending output
- identities and accumulated rows at distinct and set stages
- pending concatenated input

Resuming does not rerun an emitted prefix.

`distinct_symbols` groups rows by canonical semantic identity and merges their
relation connections before emitting one row per identity. This preserves
repeated occurrence evidence even when the result cardinality shrinks.

For individual relation occurrences, run `expand_relation` with
`output: {"type":"occurrences"}`. Each returned occurrence keeps its exact
reference and relation fact, including endpoint identities, use-site location,
and provenance. Repeated call sites remain separate rows. Read `omissions` for
the exact subject, relation kind, and structured provider evidence whenever
coverage is incomplete.

### Know why continuation stopped

A null continuation means no resumable suffix remains.

Read `terminal_reason` before interpreting the final page:

| Reason | Meaning |
| --- | --- |
| `upstream-incomplete` | A provider or discovery stage retained incomplete coverage without resumable state. |
| `output-item-too-large` | One indivisible projected item or failure exceeds the query execution output budget. |
| `checkpoint-capacity-exceeded` | The unfinished state exceeds the configured checkpoint capacity. |
| `no-progress` | The execution could not prove a progressing checkpoint. |

The transport also checks actual encoded response bytes.

If no prefix fits, the request rejects with `RESULT_TOO_LARGE`.

### Keep a continuation valid

- Keep the project and source snapshot unchanged.
- Send only the issued continuation token, without a replacement plan.
- Expect expired, evicted, or stale checkpoints to reject.
- Rediscover after source or model changes.
- Never reconstruct an opaque token.

[Read-limit settings](https://github.com/amichne/kast/blob/main/docs/hosted-read-configuration.md)
define checkpoint size, count, aggregate bytes, and lifetime.

### Check every page

- Read qualification and item failures.
- Apply source-set restrictions to `query_symbols` discovery subjects only.
- Keep expansion destinations outside that discovery restriction.
- Preserve each exact subject reference through expansion; destinations may be in other files and packages. A returned execution continuation stays bound to the query and semantic basis.
- Keep incomplete upstream coverage after buffered output drains.

## Walk relationships in a query

Add `walk` to the ordered steps and select `traversal_records` to see each
reached record with its depth and relation fact:

```json
{
  "request": {
    "action": "run",
    "source": {"type":"symbol_refs","symbol_refs":["<issued exact ref>"]},
    "steps": [{"type":"walk","relation":"callers","maximum_depth":3,"strategy":{"type":"breadth_first"}}],
    "output": {"type":"traversal_records"}
  }
}
```

`maximum_depth` accepts integers from 1 to 1000. The active hosted traversal budget
may set a lower ceiling; requests above it are rejected before traversal begins.
Omit `strategy` to use breadth-first
exploration, or select `{"type":"bounded_fan_out","maximumEdgesPerNode":20}`
to cap each node's edges. The query execution budget bounds total work and
result size. The existing traversal engine owns frontier and one-hop limits.

The result's `walk_observations` report each subject, requested relation and
depth, strategy, expanded frontier count, progress, partial expansions, and
coverage. Query execution continuation resumes unfinished work; a walk does
not issue a separate traversal token. Known records remain usable when
coverage is incomplete.

An exact edge from a terminal-qualified relation remains eligible for later query
stages. Its omission stays attached to the aggregate after known work and
buffered output finish. A terminal child has no continuation of its own; the
parent query can still have resumable downstream work. Fully consuming a child
limited only by page capacity does not leave permanent incompleteness.

Traversal cannot establish absence in omitted subtrees.

Each walk observation exposes cumulative progress:

| Field | Meaning |
| --- | --- |
| `checkpointSequence` | Ordered checkpoint number |
| `totalReads` | Reads completed so far |
| `totalEdges` | Edges retained so far |
| `maximumDepthReached` | Deepest returned edge, cumulative across pages |

Reading a depth-1 leaf with no outgoing edges increases `totalReads` without
producing depth-2 evidence. An empty second expansion therefore does not prove
that the service skipped a read. A `not_explored` remainder describes omitted
relation output at that node, not the exploration state of every returned target.

- Every resumable page must advance its checkpoint.
- `no-progress` is terminal.
- Time budgets renew for each request.
- Subject, relation, scope, strategy, and depth remain bound to the query continuation.

Use [Symbol results](/reference/symbols) to distinguish declarations from connections.

Use [Read a response](/reference/responses) before interpreting an empty result.

### Interpret time limits

Elapsed time is an observation; the time allowance is an admitted grant.

When execution exceeds the grant, the query walk:

- retains measured time and proven facts
- stops further reads
- returns `time-limit-reached`
- resumes only when unfinished work remains

An over-budget page cannot claim completion.

## Keep semantic bounds separate from page budgets

Keep operational grants separate from semantic scope:

| Control | Boundary |
| --- | --- |
| `execution_budget` | Time, provider work, results, and encoded bytes for one request |
| Relation `limit` | Relation page capacity |
| Source `entityLimit` | Source-entity page capacity |
| Walk `maximum_depth` | Requested graph depth |
| Walk `strategy` | Requested exploration policy |

A continuation may request a larger execution grant without changing its query.

A larger page grant cannot increase depth or erase a provider omission.

### Read source structure

For a hosted v4 or v5 exact selector returned by search or inspection, `source_read` accepts a
single `symbol` field. It reads the declaration with complete text, no entities,
and compact output. The selector stays opaque; pass it unchanged. A selector
that cannot be reacquired in the current IDE epoch returns a closed read failure.

The short request can override `region` (`declaration`, callable `body`,
`class-body`, or `file`), `text` (`complete`, `none`, or a `window`), `entities`
(`none` or direct `declarations`), and `format` (`compact` or `expanded`). A
window defaults to 20 lines before and after the anchor and requires
`maximumBytes`; declarations require a `limit`. The generated callable reference
contains executable request examples and the exact field schema.

Candidate and source selectors use the existing typed `anchor` request. In that
request, `region` and `entities` are selected separately.

For `entities.type: "matching"`:

- `containment: "direct"` selects direct children.
- `containment: "descendants"` also walks nested elements.
- `filters` select declarations, parameters, calls, or references.

Source containment is separate from recursive directory or package discovery.

### Choose the evidence shape

| Tool | Evidence shape |
| --- | --- |
| Query symbol output | Related declarations with retained connections |
| Query occurrence output | Individual relation facts, including repeated call sites |
| `distinct_symbols` | Changed declaration cardinality at its pipeline stage |
| Query traversal-record output | Bounded reachability with depth, strategy, progress, and coverage |

Traversal does not predict which edits break callers or which tests must run.

## Calls inside inline lambda arguments

Callers and callees attribute an inner call to the enclosing supported callable
when K2 maps the literal lambda argument to an ordinary function parameter of
the selected inline callable. This includes standard-library and user-defined
helpers; names do not authorize ownership. Every intervening lambda must pass
that check. The original inner occurrence and exact endpoints remain unchanged.

Returned or stored lambdas, ordinary callbacks, `noinline`, `crossinline`,
unresolved or ambiguous mappings, and accessor boundaries remain unsupported
or unresolved. A local named function retains its own owner. Independent
omissions remain qualified beside supported edges. Exact static ownership does
not establish runtime execution or invocation frequency.
