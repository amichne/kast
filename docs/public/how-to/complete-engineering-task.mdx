---
title: "Complete a targeted engineering task"
description: "Use compiler-grounded discovery, relationship evidence, an exact change, and project tests for one bounded task."
icon: "route"
---

Use this guide for one authorized function-body change in a connected Kotlin workspace.
Success means that the requested behavior passes its project test and the change preserves the selected scope.
Successful tool calls alone do not establish that result.

You need a ready workspace, a supported target, and an independent expected result.
For a controlled exercise, use a disposable checkout and one named regression case.

## 1. Define the expected behavior

Write the expected input and output before the source change.
Name the nearest invalid case and the source that must stay unchanged.
Run the focused project test before the change.

An unrelated compiler failure, unavailable runner, or empty selection does not establish the defect.

## 2. Discover the exact target

Use [scoped declaration discovery](/reference/search) with the known name, directory, source set, and declaration kind.
Supply known constraints before discovery.
Examine each matching signature and location before you select an issued `ref`.

Start with the execution defaults: 15,000 milliseconds and 2,000,000 work units.
Keep the response defaults of 128 results and 49,152 bytes.
If execution rejects, examine the admitted grant and finite cause before another call.

A time increase does not resolve a work-limit rejection.
The [limits reference](/reference/limits) separates execution, response, and retention controls.

## 3. Explain the affected relationships

Use the selected reference for `TRACE` or a specific relationship query.
Keep the expansion scope wide enough to include the callers that the task concerns.
Read the completion verdict and the evidence for each claimed relationship.

`TRACE` covers references, implementations or overrides, direct callers, and one further caller layer.
An unproved answer remains unproved after pagination.
Use [retained evidence](/how-to/read-retained-evidence) to inspect produced output without another semantic query.

## 4. Make the exact change

Read the target's current source.
Use [body replacement](/reference/change) only for a supported named function with a block body.
Pass the issued exact reference unchanged.
Examine the change receipt before another write.

If the outcome is uncertain, examine source and recovery evidence before another write.
After success, use the returned `freshRef` for later exact operations.

## 5. Establish the result

Examine the diff against the permitted source scope.
Use [diagnostics](/how-to/inspect-diagnostics) for the affected files.
Run the same focused project test and its invalid case.
Report the change receipt and project-test outcome separately.

Clean diagnostics do not establish every compiler identity.
A larger grant cannot repair `compiler-identity-unavailable`, stale references, or missing retained state.

## 6. Compare complete tasks

For a budget trial, repeat the same task with fixed source revisions, requests, fixtures, and host conditions.
Restore only the disposable fixture between runs.
Keep response limits equal across profiles.

Record these measures for each whole task:

| Measure | Evidence |
| --- | --- |
| Complete-answer rate | Tasks with the expected answer and passing project tests divided by all trials. |
| Total task latency | Time from discovery through the final test, including retries and recovery. |
| Intervention | Extra calls, manual budget changes, and unresolved decisions. |
| Response size | Actual encoded bytes across all calls and pages. |
| Memory | Host heap measurements and charged checkpoint bytes, reported separately. |
| IDE responsiveness | Recorded editor response and cancellation outcomes during the task. |
| Completeness and freshness | Original completion verdicts, identity evidence, and stale-state rejection outcomes. |

Include controls for a smaller work grant, a stale reference, and caller cancellation.
Keep a typed rejection distinct from a completed task.
Do not raise retention quotas without memory evidence.

This procedure defines a comparison. It does not report measured latency, heap use, or a completed native trial.
