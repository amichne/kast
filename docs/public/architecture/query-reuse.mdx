Kast shares work when the source owner can prove that reuse is sound. It keeps the original scope, identity, and evidence.

Each form of reuse has its own rules. A file inventory does not prove a relationship. A shared read cannot erase a separate path.

| Mechanism | Reused or avoided work | Proof that stays necessary |
| --- | --- | --- |
| Exact-name file exclusion | Declaration work in ordinary noncandidate files | A complete index read, then compiler refinement of candidates. |
| TRACE grouping | Repeated downstream caller reads | Matching exact capabilities and all incoming occurrence evidence. |
| Reference inventory | Repeated native search preparation within one invocation | Current authority, subject, scope, purpose, and relation confirmation. |
| IMPACT read reuse | Repeated one-hop reads at an exact value site | Every route's producer, ordered history, and final obligations. |

## Reject irrelevant files before expensive work

For an exact name, Kast can use the native word index. The read must finish before its candidate set can exclude files.

Kast then scans the bounded VFS inventory. It skips source work for ordinary files outside the candidate set.

<ExactNameDiscoveryDiagram />

The set proves which files Kast can skip. The VFS inventory still examines excluded children. For each candidate, the compiler must prove that the requested declaration exists.

<Accordion title="Exceptions and rejection rules">
  Invalid files keep the original admission path. Files too large for code intelligence keep it too. These files cannot vanish from coverage.

  If the index cannot supply a sound route for a name, Kast uses exhaustive discovery. Examples include spaced backtick names and implicit `Companion` discovery.

  A stopped or failed index read creates no exclusion object. Its prefix is not a complete candidate set.

  File, work, and retained-byte limits still apply. The index does not grant unlimited discovery.
</Accordion>

## TRACE shares expansion and keeps arrivals

`TRACE` has a fixed topology. It visits the seed, implementations or overrides, uses, and one further caller layer.

A type seed also supplies its direct callable members as seeds. That membership does not prove a call from the type to its member.

Several routes can reach the same callable. Kast groups matching callable arrivals. It then makes one downstream `CALLERS` read.

<TraceReuseDiagram />

The group keeps evidence for each reference, caller, and implementation use. Exact capabilities must match before Kast shares expansion. Each arrival keeps its evidence.

This path stops after its fixed caller layer. Use `WALK` to choose another depth.

## One prepared inventory can serve distinct relations

`REFERENCES` and `CALLERS` can need the same native reference inventory. Their semantic questions still differ.

One invocation owns the inventory slot. Its key includes current authority, subject, scope, and evidence purpose.

<ReferenceReuseDiagram />

With a matching key, Kast can examine capacity. The key does not prove an answer. The receiving relation must still prove its own meaning.

<AccordionGroup>
  <Accordion title="What enters the slot">
    The provider inventory must be eligible and start at cursor zero. Its detached locators must fit the retained-byte allowance.

    The next eligible inventory can replace the slot. The slot does not store project-wide results or continuations.
  </Accordion>
  <Accordion title="What a matching read still does">
    The receiving collector must have space for the retained inventory. The relation still proves its own meaning from the locators.

    A different key produces a miss. Without enough space, a matching inventory reports unavailable.
  </Accordion>
</AccordionGroup>

## IMPACT shares reads and keeps every route

Two routes can reach the same exact value site. Kast can reuse a settled one-hop read at that site. This includes finite rejection evidence.

Each route still keeps its own producer and ordered history. The interpreter expands the reused transfers for each route.

<ImpactReuseDiagram />

The shared read can include finite rejection evidence. A rejection never becomes a successful result with no transfers.

If a read is unfinished, Kast continues it under the existing grant. A saved prefix does not prove that the read settled.

The original ledger keeps branches, terminals, models, and unresolved obligations. Completion needs the whole ledger. A preview can show just one path.

<Info>
  Fewer native reads do not mean fewer semantic paths. A merge of reads cannot replace proof for each route.
</Info>

For reuse across source states, continue with [retention and invalidation](/reference/staleness#incremental-facts-need-new-authority).
