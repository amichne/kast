A value can cross several function boundaries without becoming a different value. This walkthrough follows one `ClientValue` through a field and a `map` callback, with each transfer attached to its source.

## What to notice

The tracked value is the constructor's `ClientValue` result. It is not the input's `id`, the whole envelope, or the whole list.

**Compiler evidence and reviewed rules answer different questions.** The compiler binds the lambda to `map.transform`. A reviewed library rule relates the callback result to a possible output element. Binding alone does not establish that relationship.

Choose **E0 · Missing proof** to remove that rule from the explanation without changing the source. The path stops at the callback result. It does not invent the missing transfer.

Choose **E3 · Two continuations** to follow either use of the same producer. Choose **E4 · Independent constant** to see why a separately constructed value is not a continuation of the original one.

**Story** shows the main transfers. **Normal** adds call crossings. **Proof** shows every expected step and its source anchor. These controls change presentation, not the underlying route.

## What this example proves

This is an interactive illustration, not a recorded Kast response. Its source and expected routes come from the repository's frozen [R1 fixtures](https://github.com/amichne/kast/tree/main/relation/intellij/testData/r1-value-flow). The missing-proof comparison deliberately withholds one expected transfer.

The example does not run Kotlin or query an IDE. It contains no captured compiler identities or investigation coverage ledger. Reaching its final step does not establish a complete investigation.

Kast's static relationships do not prove that a callback ran, that a branch can run, or how often code runs. [Program tracing](/reference/program-tracing) defines those limits. [Evidence boundaries](/reference/evidence-boundaries) explains what an answer can establish.
