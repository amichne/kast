Use this guide for one authorized function-body change in a connected Kotlin workspace. Success means that the requested behavior passes its project test and the change stays within the selected scope. Successful tool calls alone do not establish that result.

You need a ready workspace and a supported target. Define the expected result from outside the code under test. For a controlled exercise, use a disposable checkout and one named regression case.

1. [Define the expected behavior.](#1-define-the-expected-behavior)
2. [Find the exact target.](#2-discover-the-exact-target)

## 1. Define the expected behavior

Write the expected input and output before the source change. Name the nearest invalid case and the source that must stay unchanged. Run the focused project test before the change.

An unrelated compiler failure, a missing runner, or a test selection with no cases leaves the defect unproved.

## 2. Discover the exact target

Use [scoped declaration discovery](/reference/search) with the known name, directory, source set, and declaration kind. Examine each matching signature and location before you select an issued `ref`.

The default `RUNNER_CONTROLLED` mode has no implicit semantic work or time limit. Its default output page holds up to 128 rows and 49,152 bytes. If execution rejects, examine the specific cause before another call.

An explicit `BOUNDED` mode uses work and time grants. More time does not fix a work-limit rejection. The [limits reference](/reference/limits) separates execution, response, and retention controls.

## 3. Explain the affected relationships

Use the selected reference for `TRACE` or a specific relationship query. Keep the expansion scope wide enough to include the callers that the task concerns. Read the completion verdict and the evidence for each claimed relationship.

`TRACE` covers references, implementations or overrides, direct callers, and one further caller layer. More output pages do not change the completion verdict. Use [retained evidence](/how-to/read-retained-evidence) to inspect produced output without another semantic query.

## 4. Make the exact change

Read the target's current source. Use [body replacement](/reference/change) only for a supported named function with a block body. Pass the issued exact reference unchanged. Examine the change receipt before another write.

If the outcome is uncertain, inspect the source and recovery evidence before another write. After success, use the returned `freshRef` for later exact operations.

## 5. Prove the result

Examine the diff against the permitted source scope. Use [diagnostics](/how-to/inspect-diagnostics) for the affected files. Run the same focused project test and its invalid case. Report the change receipt separately from the project-test result.

Clean diagnostics do not prove every compiler identity. A larger grant cannot repair `compiler-identity-unavailable`, stale references, or missing retained state.

## Compare execution profiles

The source-change task ends with the scoped diff, receipt, and project-test result.
To compare execution profiles, use the contributor procedure for [complete engineering tasks](https://github.com/amichne/kast/blob/main/docs/development.md#compare-complete-engineering-tasks).
That separate experiment keeps requests, fixtures, host conditions, and measurements comparable.
