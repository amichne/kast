Use this guide for one authorized function-body change in a connected Kotlin workspace. Success means that the requested behavior passes its project test. The change also keeps the selected scope. Successful tool calls alone do not prove that result.

You need a ready workspace and a supported target. Define the expected result from outside the code under test. For a controlled exercise, use a disposable checkout and one named regression case.

## 1. Define the expected behavior

Write the expected input and output before the source change. Name the nearest invalid case and the source that must stay unchanged. Run the focused project test before the change.

An unrelated compiler failure does not prove the defect. Neither does a missing runner or a test selection with no cases.

## 2. Discover the exact target

Use [scoped declaration discovery](/reference/search) with the known name, directory, source set, and declaration kind. Supply known constraints before discovery. Check each matching signature and location before you select an issued `ref`.

The default `RUNNER_CONTROLLED` mode has no implicit semantic work or time limit. Its default output page holds up to 128 rows and 49,152 bytes. If execution rejects, examine the specific cause before another call.

An explicit `BOUNDED` mode uses work and time grants. More time does not fix a work-limit rejection. The [limits reference](/reference/limits) separates execution, response, and retention controls.

## 3. Explain the affected relationships

Use the selected reference for `TRACE` or a specific relationship query. Keep the expansion scope wide enough to include the callers that the task concerns. Read the completion verdict and the evidence for each claimed relationship.

`TRACE` covers references, implementations or overrides, direct callers, and one further caller layer. Reading more pages does not make an unproved answer proved. Use [retained evidence](/how-to/read-retained-evidence) to inspect produced output without another semantic query.

## 4. Make the exact change

Read the target's current source. Use [body replacement](/reference/change) only for a supported named function with a block body. Pass the issued exact reference unchanged. Check the change receipt before another write.

If the outcome is uncertain, check source and recovery evidence before another write. After success, use the returned `freshRef` for later exact operations.

## 5. Prove the result

Check the diff against the permitted source scope. Use [diagnostics](/how-to/inspect-diagnostics) for the affected files. Run the same focused project test and its invalid case. Report the change receipt. Report the project-test outcome on its own.

Clean diagnostics do not prove every compiler identity. A larger grant cannot repair `compiler-identity-unavailable`, stale references, or missing retained state.

## 6. Compare complete tasks

For a budget trial, repeat the same task. Keep source revisions, requests, fixtures, and host conditions fixed. Restore only the disposable fixture between runs. Keep response limits equal across profiles.

Record these measures for each whole task:

- **Share of tasks that complete:** Count tasks with the expected answer and passing project tests. Divide by all trials.
- **Whole-task time:** Measure from discovery through the final test. Include retries and recovery.
- **Extra steps:** Count extra calls, manual budget changes, and unresolved decisions.
- **Response size:** Actual encoded bytes across all calls and pages.
- **Memory:** Report host heap use and charged checkpoint bytes as distinct measures.
- **Editor response:** Record how the editor responds and how cancellation ends during the task.
- **Coverage and current state:** Keep original completion verdicts, identity evidence, and stale-state rejection outcomes.

Include controls for a smaller work grant, a stale reference, and caller cancellation. Keep a typed rejection distinct from a completed task. Do not raise retention quotas without memory evidence.

These steps define a comparison. They do not report measured time, heap use, or a completed native trial.
