# Hosted semantic-query reproduction

On 2026-09-10, the unchanged v0.38.0 CLI and hosted plugin reproduced the reported positive reads and both qualified relation shapes on synthetic Kotlin/Java fixtures. The three reported `BUDGET_EXCEEDED / SEMANTIC_READ` failures were **not reproduced**. They returned useful exact items with incomplete discovery coverage. Subsequent instrumentation identified a property-name enumeration cap, not elapsed/work/result/byte exhaustion, in these runs.

The [runner and commands](../../experiments/host-observation/SEMANTIC_REPRODUCTION.md) are opt-in. Raw receipts remain in the local evidence directory `kast-semantic-reproduction-evidence`; directory names below identify each experiment. They contain commands, inputs, responses, process outcomes, runtime hashes, expectations, host/epoch and coverage. No enterprise source or credentials were used.

## Causes and counterfactuals

**Enumeration, not selected result count.** The smallest tested fixture already qualified ALL C despite its one-result oracle. `diagnostic-base` records 10,001 property names visited, 10,000 retained matching names, five property candidates collected and filtered, and `NAME_CAP`. It also collects/filters 22 class and 20 function candidates before projecting the one alias. Exactly one compiler refinement follows. The otherwise identical exact request collects one direct-index candidate and completes; fuzzy visits 76,466 property names, matches none of them, and completes. The cap counts matching names, not all visited names.

The source path is [native discovery](../../symbol/intellij/src/main/kotlin/io/github/amichne/kast/symbol/intellij/discovery/IntellijNativeDiscoveryQuery.kt): native scope is supplied during enumeration; directory/root ownership, package and declaration-kind admission also run after candidate collection, before projection. [Scope compilation](../../symbol/intellij/src/main/kotlin/io/github/amichne/kast/symbol/intellij/discovery/IntellijSearchScopeCompiler.kt) narrows readable source sets/roots. [Direct exact indexes](../../symbol/intellij/src/main/kotlin/io/github/amichne/kast/symbol/intellij/discovery/IntellijExactNameIndexes.kt) avoid name enumeration. The caller already supplies a project ID filter. These measurements do not prove why the upstream property contributor exposes so many names, or that enumeration work is proportional to the selected package. They do prove that type-alias-only output still pays for and can be qualified by irrelevant contributor enumeration.

`v038-names-1000`, `v038-functions-1000`, and `v038-functions-5000` independently scale unrelated declarations inside the same admitted module count, keeping selected source/count fixed. ALL C remains qualified minimum 1, exact/fuzzy complete, on first and warm queries. The instrumented 5,000-function comparison retains that property-name cap and independently hits `CANDIDATE_CAP` in the function contributor: 5,011 names visited, 10,000 candidates collected, all 10,000 filtered before projection. These native caps are distinct from the 100,000-unit work budget, although the public qualification merges them. No natural timeout was found in this range; there is no asserted minimum timeout-producing load. The base's single unrelated class has a different synthetic name from the generator's default, without changing the selected package.

**Module admission is separate.** `v038-modules-84` has 87 Gradle projects and 259 IDEA modules. ALL, exact and fuzzy reject `NAMED_SOURCE_SCOPE_REJECTED / CAPTURE_LIMIT / MODEL_CAPTURE`. Explicitly removing one unrelated Gradle project and reimporting yields 86 projects and 256 IDEA modules (`v038-modules-83`): exact/fuzzy succeed, ALL still qualifies. [Model capture](../../workspace/intellij-read/src/main/kotlin/io/github/amichne/kast/workspace/intellij/read/LiveNamedGradleSourceScopeCapture.kt) enforces the module bound before semantic execution. Raising it cannot extend either deadline. `diagnostic-modules-84` confirms 87 imported projects, 259 IDEA modules, `MODULE_ADMISSION_LIMIT`, and no semantic entry in a 0.84 ms request. Explicitly restoring 256 modules recovers exact lookup on the same hosted service (`module-recovery-audit.json`).

**Deadline ordering is possible, but did not cause these ALL results.** [The executor](../../workspace/intellij-read/src/main/kotlin/io/github/amichne/kast/workspace/intellij/read/hosted/HostedQueryExecutor.kt) starts the outer timeout before project/epoch/model capture. [The service](../../workspace/intellij-read/src/main/kotlin/io/github/amichne/kast/workspace/intellij/read/hosted/HostedQueryService.kt) then enters [the transaction](../../workspace/intellij-read/src/main/kotlin/io/github/amichne/kast/workspace/intellij/read/hosted/HostedReadTransaction.kt), and [canonical evaluation](../../runtime/hosted/src/main/kotlin/io/github/amichne/kast/runtime/hosted/HostedCanonicalQuery.kt) gets a fresh inner budget. Instrumented ALL C enters with 1,998.78 ms remaining and spends 483.60 ms in semantic read; exact spends 2.01 ms and fuzzy 451.33 ms. Unchanged provider/CLI end-to-end ALL A/B/C times were about 1,183/1,145/1,020 ms and include process overhead. A virtual-time test proves 600 ms of capture leaves 1,400 ms, so an 1,800 ms inner computation is rejected by the outer deadline; the same executor recovers. That is deterministic mechanism evidence, not a native timeout reproduction.

**Java callee projection is inherited.** `v038-java` changes only `trace` to call the Kotlin helper plus `java.lang.System.nanoTime()`. First and warm queries preserve the helper and qualify coverage in unrestricted, directory and package requests; exact recovery succeeds. `diagnostic-java` observes `K2_NON_KOTLIN_PSI → RELATION_UNRESOLVED_TARGET`. The symbol resolves and has PSI, but [K2 projection](../../relation/intellij/src/main/kotlin/io/github/amichne/kast/relation/intellij/IntellijK2RelationProjection.kt) requires `KtNamedDeclaration`. [Callee search](../../relation/intellij/src/main/kotlin/io/github/amichne/kast/relation/intellij/IntellijK2RelationSearch.kt), [collection](../../relation/intellij/src/main/kotlin/io/github/amichne/kast/relation/intellij/IntellijRelationCollector.kt) and [public coverage](../../query/service/src/main/kotlin/io/github/amichne/kast/query/service/QueryExecutionState.kt) preserve that limitation. The same cast and unresolved mapping exist in v0.37.2; this is not evidence of a new Java regression.

**Java-only references are an independent inherited limitation.** `v038-java-references` adds a Java method returning and constructing the manager. `diagnostic-java-references` records `NON_KOTLIN_REFERENCE → RELATION_UNSUPPORTED_ITEM`, yielding zero exact items with incomplete coverage. Removing the Java source (the base control) restores complete empty output; the unused marker remains complete in both fixtures. The `reference as? KtReference` boundary and unsupported mapping also exist in v0.37.2. This is a candidate explanation reproduced synthetically, not proof of the enterprise manager's callers.

**Resolved Kotlin outside discovery scope reveals a separate contract mismatch.** `v038-outside` adds one resolvable Kotlin callee in the core module. Unrestricted expansion returns both exact edges, complete. Directory-scoped discovery returns one edge qualified with `CALLEE_OUTSIDE_NATIVE_SCOPE`; package-scoped discovery returns one edge **complete**, with `TARGET_OUTSIDE_PACKAGE` in diagnostics. The installed schema says discovery scope does not restrict expansion destinations. The corrected oracle therefore expects both edges in all three cases. The package exclusion branch was added by `5c8bbe554` between v0.37.2 and v0.38.0; its implementation **changed**, but native comparative regression evidence is blocked by the older public route. The directory unsupported-target branch is inherited. Neither exclusion is time/work exhaustion.

## Delivery and correction scope

The production edits only thread an opt-in observation capability through existing boundaries. One bounded receipt records stage/outcome after drainage; finite reasons distinguish admission, name/candidate caps, time/work/result/byte limits and unsupported semantics. Compiler/refinement counts and host/epoch correlation are retained without source payloads. Instrumented hashes differ from the release; their timings are diagnostic measurements.

The smallest evidence-backed follow-up is to preserve discovery/expansion scope separation for the demonstrated Kotlin case, with a focused public-contract test for the missing second edge. Separately, select contributors that can satisfy an already-proven declaration-kind restriction before broad enumeration. Validate this against ALL C without changing limits. Java target/reference support requires an explicit supported representation; until then keep qualified coverage. There is no evidence here justifying a blanket budget increase or a timeout fix for the reported enterprise case.

Verification: fixture compilation for every variant; receipt/oracle checks; focused executor/diagnostic, discovery and relation tests; `productBuildGate`; `knowledgeImpact`; `verifyKnowledgeBase`. Native first/warm reads used existing indexes without cache invalidation, worker fallback, query-triggered import or artificial delays. Environment receipts and generated fixtures remain outside public source. The original user's dirty checkout was preserved; implementation is isolated at the inspected release.

Cleanup verified the original IDEA process and user project remained open, the original plugin directory/version was restored, and the diagnostics property was cleared. Exact lookup succeeded after plugin restoration (explicitly labelled mixed CLI/plugin liveness evidence). Only the eight disposable fixture projects were closed. The local evidence `index.json` links baseline, diagnostic, excluded, blocked and verification receipts.
