Direct MCP carries Kast tool calls over stdio. The client starts the process in the intended repository directory. After negotiation, it admits the catalog.

## Catalog

`tools/list` supplies each tool's name, `inputSchema`, and `outputSchema`. Those installed schemas govern the session.

| Tool | Purpose |
| --- | --- |
| `query_symbols` | Declarations, source, relationships, and composition. |
| `check_diagnostics` | IDEA diagnostics for a path. |
| `health_check` | Workspace binding and readiness. |
| `add_declaration`, `replace_body` | Targeted source changes. |

Direct MCP omits `workspace_lifecycle`. Hosted App Server supplies that distinct tool to control projects.

Tool discovery shows which tools are available. It does not prove that the IDEA project is ready. It does not prove that a semantic query is complete.

## Call and result

`tools/call` selects a catalog tool and its input object. This example asks whether the workspace is ready. It does not ask for declaration evidence.

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {"name": "health_check", "arguments": {}}
}
```

The reply puts display text in `content[]`. It puts the checked tool document in `structuredContent`. `isError` reports a failed tool call.

For semantic tools, `structuredContent` is the canonical tool document. It has its own status: complete, qualified, or rejected.

A failed tool call can omit the document. `health_check` uses a distinct readiness shape with its own schema.

Decode both the wrapper and the selected tool document. A successful JSON-RPC exchange does not make an incomplete semantic answer complete.
