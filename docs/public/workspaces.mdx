Use `kast` to manage the installation. Ask semantic questions through your agent.

## Inspect the installation

```shell
kast status
```

Status distinguishes recorded registrations from live observations. Registration does not establish a running process or ready workspace.

## Upgrade

Save your work and finish active calls:

```shell
kast upgrade
```

Upgrade stops owned services and interrupts sessions. Restart IDEA and connected agents. Existing calls and sessions do not resume across upgrade.

## Stop and reinstall

Close the selected IDEA and affected agent connections. Then run:

```shell
kast stop --json
kast reinstall --json
```

`stop` fences calls and automatic restart, disables the coordinator, and waits up to 30 seconds for recorded calls and MCP sessions. It preserves payload, configuration, and registrations.

For forced retirement of recorded tool processes, use `kast stop --force --json`. Kast verifies PID start time, main class, and installed library digests before signaling.

Running IDEA returns `REJECTED` with `HOST_RESTART_REQUIRED`. Quit it and repeat. Shutdown rejection keeps the fence and prevents payload replacement.

`reinstall` verifies shutdown, installs the recorded version, activates the coordinator, and restores integrations. Failed activation restores the fence and returns `REINSTALLATION_PENDING` with the failed stage. Inspect `kast status --json` before retrying recovery. Reload agents after success. Writes are never replayed.

Rerunning the published installer also resumes a valid shutdown left by `kast stop` after installation completes. Routine installation retires the prior service before checking the state to retain, so transient live entries and a stopped service's retained configuration do not block replacement. If retirement, state retention, or payload activation fails, Kast attempts to restart the prior service and reports the recovery outcome.

An existing tool session rechecks a previous unavailable or incompatible Host or plugin when its next request needs the workspace. Restart IDEA after installing a Host update to load it. Recovery still requires the installed compatibility contract and exact project readiness before dispatching the request. It does not replay semantic execution.

Preparation lookup history is bounded. Retries can retire older terminal lookup records while preserving held results and their original observations. Current roots and pending work remain protected. A lookup after its record is retired returns `UNKNOWN_OPERATION`; this does not distinguish an expired identifier from one that was never issued.

<Accordion title="Lifecycle result contract">
  JSON stdout contains one `type`: `STOPPED`, `REINSTALLED`, `REJECTED`, or `REINSTALLATION_PENDING`. Stage observations use stderr. Rejected and pending results exit with code 1.

  The schema ships at `installation/share/kast/schema/management-lifecycle.schema.json`. Older payloads without fence capability reject before effects. Upgrade through the published installer.
</Accordion>

## Force reset

<Note>
  Force reset erases installed state. Erased data has no rollback.
</Note>

```shell
kast uninstall --force --json
kast reinstall --force --json
```

Reset bypasses old ownership checks. It fences startup, records a recovery location, and moves the directory aside before retiring scoped Kast processes. Shared IDEA and Gradle processes remain under your control. Failed retirement preserves old contents and reports `recoveryPath`.

Force reset also removes legacy `$HOME/.kast` state, historical `.kast-*` artifacts under `$HOME/.local/share`, and the public command. Stable lock files remain.

Force reinstall selects the latest release from the recorded stable or developer channel. It installs both Control and Host and repairs valid recorded connections.
Success returns `RESET_REINSTALLED`, the new version, service `generation`, and public `command` at `$XDG_CONFIG_HOME/kast` or `$HOME/.local/bin/kast`.
Restart IDEA and affected agents after installation.

The public installer uses the same reset with `--force`. Developer installation requests it automatically.
The installer examines the downloaded archives before reset. An older selected release can use newer recovery code. The installer examines its checksum and keeps the selected installation version.
`--dry-run` preserves files and registrations.

<Accordion title="Reset scope and results">
  Reset unlinks symlinks. It does not read their targets. Filesystem roots, HOME, and its ancestors reject deletion.
  Reset preserves process identity evidence and stops scoped processes before erasure.

  The exterior lock serializes cleanup. Failed retirement keeps the old payload and reports `recoveryPath`.
  Installation starts after reset completes. Success needs a qualified payload and service readiness.
  An installation failure returns `RESET_REJECTED`. A readiness failure returns `RESET_REINSTALLATION_PENDING`.

  JSON variants are `REMOVED`, `RESET_REINSTALLED`, `RESET_REINSTALLATION_PENDING`, `RESET_RETAINED`, `RESET_RECOVERY_REQUIRED`, and `RESET_REJECTED`.
  Unsuccessful results exit with code 1. The lifecycle schema defines these variants.
</Accordion>

## Change agents

```shell
kast connect pi
kast disconnect copilot
```

Multiple agents can connect. Restart a disconnected agent to unload its integration. See [connection conflicts](/agent-harnesses#a-connection-already-exists).

## Uninstall

```shell
kast uninstall
```

Read ownership and recovery failures before retrying.

## Explicit workspace control in the hosted App Server

`workspace_lifecycle` inspects, presents, releases, or closes a selected project. It is absent from direct MCP and Tool RPC. Inspect the installed schema and approval requirements before an action. Disconnect, release, and close have separate effects.
