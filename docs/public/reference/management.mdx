<a id="inspect-the-installation" />

## 1. Inspect the installation

```shell
kast status
```

Read registrations and live service state separately. Registration identifies an installed integration rather than a ready workspace or live semantic authority.

<a id="upgrade" />

## 2. Upgrade a compatible installation

Wait for active calls to finish. Start the upgrade after you save source work.

```shell
kast upgrade
```

Upgrade stops owned services and interrupts sessions. Restart IDEA and clients after success, then start fresh sessions and calls.
Upgrade does not start a Codex broker. Its MCP session starts IntelliJ preparation when the client connects.
If the Codex plugin is installed, run `kast plugin codex` to refresh its cached files.

<Accordion title="Upgrade Control without replacing Host">
  Control supplies the command, coordinator, agent adapters, and sessions. Host supplies the IDEA plugin and semantic runtime.

  ```shell
  kast upgrade --control-only
  ```

  This command needs a running compatible Host. It preserves IDEA and its plugin files. Control sessions can stop during the upgrade.

  Kast examines the Host contract before shutdown and after startup. Failure restores the previous Control or reports that recovery is necessary.

  [Compatibility](/reference/compatibility) depends on protocol, registry, schema, capabilities, and IDEA admission. Equal version numbers do not establish compatibility.
</Accordion>

<Accordion title="Load a Host update or migrate an older installation">
  For Host-only installation, use the public installer with `--host-only --version <host-version>`. Restart IDEA to load the plugin.

  Hosted changes use a private local endpoint and native workspace admission. Installation does not create approval keys.

  An older Host needs a matching Control contract. Upgrade both components. Restart IDEA before a fresh agent session.

  Read [the keyless migration](https://github.com/amichne/kast/blob/main/app-server/docs/compatibility.md#keyless-hosted-change-migration) for the compatibility gate.
</Accordion>

## 3. Stop and reinstall a recorded version

Before stop, quit the selected IDEA instance. Close affected agent connections, then request retirement and recorded-version recovery.

```shell
kast stop --json
kast reinstall --json
```

`stop` fences new calls and automatic restart before retirement. It disables the coordinator and waits up to 30 seconds for recorded calls and MCP sessions.

The installed payload, configuration, and registrations stay in place. `--force` requests retirement of recorded tool processes after process identity admission.

Kast examines PID start time, main class, and installed library digests before a signal. A live IDEA returns `HOST_RESTART_REQUIRED`.

If shutdown rejects, preserve the fence. Payload replacement cannot continue through failed shutdown.

`reinstall` installs the recorded version after shutdown succeeds. It removes the exact owned shutdown fence and restores supported integrations.
It does not start a coordinator. Recorded Codex registrations migrate through the plugin owner.

If payload completion fails, Kast keeps the fence and reports its stage. Inspect `kast status --json` before another recovery try.

The published installer can resume valid shutdown. Routine replacement retires the predecessor before it examines the state to keep.

If retirement or payload replacement fails, recovery can restore the predecessor. The result reports that recovery outcome.

### Lifecycle result contract

JSON stdout reports `STOPPED`, `REINSTALLED`, `REJECTED`, or `REINSTALLATION_PENDING`. Stage evidence uses stderr, and unsuccessful results exit with code 1.
Force reinstall reports `RESET_INSTALLED` after payload and fence completion. That result carries no service generation or readiness claim.

The installed `management-lifecycle.schema.json` owns exact variants. Older payloads without fence capability reject before lifecycle effects.

### Workspace recovery after replacement

A later authorized demand can reexamine an unavailable or incompatible Host. A Host update still needs an IDEA restart before new semantic admission.

Preparation history does not become permanent readiness authority. Its finite lookup storage can reclaim older terminal records while held results remain intact.

A reclaimed identifier returns `UNKNOWN_OPERATION`. That result cannot distinguish an expired record from an identifier Kast never issued.

No recovery path replays a write. [Lifecycles](/reference/lifecycles) describes preparation and request settlement.

## 4. Reset only after ownership recovery fails

Force reset erases installed state and has no rollback after erasure. Use it only when that reset scope matches your recovery need.

```shell
kast uninstall --force --json
kast reinstall --force --json
```

Reset fences startup and moves the installation aside before scoped process retirement. It preserves a recovery location if retirement fails.

Shared IDEA and Gradle processes remain under your control. Stable exterior lock files remain in place.

Reset removes legacy `$HOME/.kast` state, historical `$HOME/.local/share/.kast-*` artifacts, and the public command.

It unlinks symlinks without reads of their targets. It rejects filesystem roots, HOME, and ancestors of HOME as deletion targets.

Force reinstall selects the latest release from the saved channel. It installs Control and Host and repairs valid recorded connections.

Success returns `RESET_INSTALLED`, version, installation path, and command path. Restart IDEA and affected clients after success.

The public installer uses this reset with `--force`. Developer installation requests it automatically after archive admission.

`--dry-run` preserves files and registrations. Version-pinned installation can use newer checksum-admitted recovery code while it keeps the selected installation version.

### Reset outcomes

The closed variants include `REMOVED`, `RESET_INSTALLED`, `RESET_REINSTALLATION_PENDING`, `RESET_RETAINED`, `RESET_RECOVERY_REQUIRED`, and `RESET_REJECTED`.

Installation failure returns `RESET_REJECTED`. Payload or fence failure after staging returns `RESET_REINSTALLATION_PENDING`. Unsuccessful outcomes exit with code 1.

If a result reports `recoveryPath`, preserve that path. Examine the named failed stage before another reset.

## Change agents

```shell
kast connect pi
kast disconnect copilot
```

Restart a disconnected client to unload its integration. Other clients and the shared daemon keep their separate lifecycle.

## Uninstall

```shell
kast uninstall
```

If removal fails, preserve ownership and recovery evidence. Resolve its named cause before another try.

## Explicit workspace control in the hosted App Server

Hosted `workspace_lifecycle` supplies inspection, presentation, release, and project closure. Direct MCP and Tool RPC omit that tool.

Before a project action, examine the installed schema and its authorization needs. Disconnect, release, and project closure produce different effects.
