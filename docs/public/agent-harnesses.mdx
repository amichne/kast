A harness should load the contract from the Kast executable it will invoke.
Run `kast --schema`, then consume `serverProjection`. This supplies the tool
catalog and argument vectors for that installation.

For the included integration, run `kast codex` from your repository root and
continue with [Search declarations](/search). The rest of this page is for
implementing another harness.

## Bind the catalog once at startup

<Steps>
  <Step title="Admit the installed projection">
    Validate the projection and its versions. Missing, malformed, unsupported,
    or contradictory data must stop catalog registration. The current server
    projection is version 10; CLI invocation bindings are version 3. A version
    number alone does not prove the rest of the contract.
  </Step>
  <Step title="Join by tool name">
    Match `hostedBootstrap.tools` with `cliInvocations.operations` by `toolName`,
    then verify the canonical operation ID. Require exactly one binding per
    tool. Multiple search tools intentionally share `query.run`, so operation
    identity alone cannot identify an invocation.
  </Step>
  <Step title="Register the complete tool definition">
    Preserve namespace, policy, order, name, description, input/output schemas,
    effect, approval policy, deferred-loading hint, and execution budget. Use the
    admitted argument vector and repository root when invoking the executable;
    do not interpolate input into a shell command.
  </Step>
  <Step title="Validate and return the whole result">
    Send one JSON input on stdin. Admit the output against that tool's output
    schema and preserve both result layers. Give the model the semantic status,
    payload, qualification, item failures, and unchanged references.
    [Read a response](/reference/responses) describes the dispatch rules.
  </Step>
</Steps>

Requalify when the provider starts. If the executable or projection changes,
construct a new catalog instead of keeping bindings from the prior installation.

## Choose what the agent sees

| Availability | Tools | Why |
| --- | --- | --- |
| Eager defaults | `search_classes`, `search_functions`, `search_declarations`, `check_diagnostics` | Directly express common reader intent |
| Deferred defaults | `query_symbols`, `source_read`, `semantic_query`, `impact_analyze` | Add pipelines, source, relations, and traversal when needed |
| Deferred changes | `change_plan`, `change_apply`, `change_recover` | Keep planning and approval attached to stored changes |
| Explicit opt-in | `symbol_lookup`, `symbol_inspect` | Expose candidate discovery and refinement when required |

Keep lifecycle, synchronization, topology setup, status, and broker administration
outside the agent tool catalog. Reads use the existing saved IDEA project and
report a typed blocker when its evidence cannot be admitted.

## Preserve approval as an operation

`change_plan` needs no approval. `change_apply` and `change_recover` each need
approval of the exact stored plan. A plan ID or an `EXPLICIT` catalog field does
not constitute approval.

The included integration loads the stored preview, emits a native file-change
preview, and requests approval from the current controller. Decline,
cancellation, lost control, and expiration reject before writing. A custom
harness must implement the approval integration specified by the installed
contract; an ordinary CLI invocation cannot substitute for it.

Follow [Change source](/change) for broker trust, plan lifetime, apply states,
and recovery. Preserve qualified mutation outcomes: `applied_unverified` and
`recovery_required` cannot be rendered as verified success.

## Configuration and migration

<AccordionGroup>
  <Accordion title="Configure the selected catalog">
    `KAST_APP_SERVER_TOOLS` accepts an exact, non-empty, duplicate-free,
    comma-separated subset of installed tool names. Unknown names reject startup.
    Its default selection is:

    ```text
    search_classes,search_functions,search_declarations,query_symbols,source_read,semantic_query,impact_analyze,check_diagnostics,change_plan,change_apply,change_recover
    ```

    Catalog selection does not grant mutation authority. Direct candidate tools
    remain opt-in. Set `KAST_ENABLE_APP_SERVER=0` to disable the integration.
  </Accordion>
  <Accordion title="Find the configuration used by a launch">
    The installer saves App Server settings in the selected release's
    `config/environment`, normally reached through
    `~/.local/share/kast/current/config/environment`. Process values override
    saved values. Fresh installations materialize defaults, including `KAST_DEBUG=0`.

    `kast app-server status` reports the resolved `launchEnvironment` snapshot,
    saved configuration, and service log paths. `KAST_DEBUG=1` also streams
    bounded launch diagnostics to stderr.
  </Accordion>
  <Accordion title="Migrate an older query integration">
    Recreate persisted catalogs with the matched executable and broker.
    `kast.query` and `kast.diagnostic_check` are not aliases in the new agent
    catalog. Use the intent tools. The explicit legacy `kast query run` CLI
    grammar still exists; it is distinct from the new agent registration.
  </Accordion>
</AccordionGroup>
