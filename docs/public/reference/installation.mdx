Use the remote installer for initial setup, then `kast upgrade` for updates.
Kast manages its own Host on macOS ARM64 and Linux x86-64. Desktop IDEA is not a prerequisite.

<Warning>
  This page describes the managed-runtime contract under implementation. Native acceptance and publication are not yet complete. The remote main installer is not evidence that this branch is available.
</Warning>

<span id="before-you-install" />

## Requirements

Use a supported machine, a Kotlin Gradle project, Bash, curl, and standard archive and checksum utilities.
Kast supplies its private interpreter, Java runtime, and IntelliJ analysis runtime. No user Python, uv, or pip installation is required.
The bootstrap downloads pinned interpreter and dependency bytes, so setup still requires network access.
Your project still supplies its build configuration, dependencies, and any required credentials.

<a id="install" />

## Remote initial install

```shell
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/amichne/kast/main/install.sh)" -- --channel preview
```

The installer selects one complete product: an immutable vendor base and exact Control, Host, and agent components.
It verifies the selected records and bytes before activation. A missing component is a failure, not permission to mix builds.
Installation does not grant trust to a project or start its Host.

The installation directory is `$HOME/.local/share/kast`.
The command path is `$XDG_CONFIG_HOME/kast` when `XDG_CONFIG_HOME` is nonempty, or `$HOME/.local/bin/kast` otherwise.
Add the printed command directory to `PATH` if needed. The installer does not edit shell profiles.

Use [agent setup](/reference/integrations) after installation. No desktop plugin installation or restart is needed.

### Install a local product globally

On macOS ARM64, build and qualify a clean committed checkout first:

```shell
mise exec -- uv run --locked --project packaging python packaging/local_product_install.py \
  build --source /path/to/clean/checkout --output /absolute/path/to/product
```

From a checkout, pass a local product directory to the same installer:

```shell
/bin/bash ./install.sh --local-artifact /absolute/path/to/product --dry-run --json
/bin/bash ./install.sh --local-artifact /absolute/path/to/product --json
```

The directory contains `build-record.json` and a `payload/` directory with the selected platform's recorded artifacts.
These include the setup bundle, runtime archive, native qualification receipt, and runtime base when the record requires one.
A Control archive or setup bundle alone is not a complete product.
Local build records identify only the qualified platform. They record local provenance, not GitHub runs or release qualification.

This uses the normal installation and command paths above, not a separate contributor installation.
The installer pins the record's exact product identity and verifies the same digests, archive inventories, and qualification evidence as remote setup.
It reads product bytes locally and never falls back to GitHub for missing files.
The bootstrap still downloads its pinned private interpreter and dependency; this option does not make setup offline.
Do not combine `--local-artifact` with `--channel`, `--version`, or `--commit`.
`kast upgrade --repair` rejects a local product with `LOCAL_ARTIFACT_REQUIRED` before effects, because its bytes exist only in the local directory.

<Warning>
  Desktop IntelliJ IDEA Hosts and user-space plugin installation are deprecated and targeted for removal.
  The desktop component installer and checkout shell adapters are retired. Use `install.sh` for managed product setup.
  Existing 0.51.x desktop Hosts and their wire values remain supported for compatibility.
  Use managed headless Hosts with private workspace state and automatic workspace creation instead.
</Warning>

### Replace a pre-product installation

Releases 0.51.3 and older have no product selection record, so the installer rejects them and prints `LEGACY_PURGE_AVAILABLE`.
To remove such an installation before the new product installs, add `--purge-legacy`:

```shell
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/amichne/kast/main/install.sh)" -- --channel preview --purge-legacy --dry-run --json
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/amichne/kast/main/install.sh)" -- --channel preview --purge-legacy --json
```

The dry run changes nothing. It reports the old version, the processes to stop, and the paths to delete.
The purge runs only after the new product is downloaded and verified. It then takes these steps in order:

1. It verifies the old payload, its `management.json` receipt, and the launcher digest. It then runs the launcher's `uninstall --force --json`. Any outcome other than `REMOVED` stops the purge.
2. It stops desktop IDEs that still run the removed `kast-ide-hosted` plugin, and Hosts that run from an old runtime. Each process gets `SIGTERM`, then `SIGKILL` after 40 seconds. A process that survives both stops the purge.
3. It deletes old runtimes, workspace containers, the reset lock, and socket roots under `/tmp`. It also deletes `kast-ide-hosted` copies in desktop JetBrains profiles.

Unsaved IDE work can be lost, so save it first.
The first semantic request afterward imports the workspace again, including a fresh private Gradle home, which can take several minutes.
Agent registrations are left unchanged because the new product recreates the launcher paths they use.
Developer `0.0.N` builds and unrecognized files reject without changes.

Explicit MCP setup uses target-specific dependencies packaged with the selected Control build.
It verifies the private interpreter and exact dependency inventory before preparation. It does not invoke pip, uv, or a dependency solver.
Upgrade, recorded recovery, and product removal reuse admitted private support; missing or changed bytes reject without an ambient interpreter fallback.

## 1. Install the selected release

```shell
kast versions
kast upgrade --channel preview --dry-run
kast upgrade --channel preview
```

`preview` selects a complete preview build. `stable` selects a complete stable build.
`main` remains an alias for `preview`; new commands use `preview`.
A catalog entry identifies the selected product and its platform. Component publication alone does not establish a selectable product.

### Pin a published build

Use one selector: `--channel`, `--version`, or `--commit`.
Copy an exact version or revision from `kast versions`:

```shell
kast upgrade --version VERSION
kast upgrade --commit REVISION
```

An exact selector records a pin. An unqualified upgrade rejects a pin with `PINNED_BUILD`.
Use `kast upgrade --channel preview` to follow preview builds again.
Use `kast upgrade --repair` to restore the exact installed product, not to select a newer build.

## 2. Inspect installed state

The managed Host loads its plugin on demand. No desktop action is required.

```shell
kast status --json
kast status --all --json
```

Status separates installed product identity, update policy, unfinished transactions, and workspace Host observations.
It does not start a Host, grant trust, repair state, or contact release servers.
A recorded workspace is not proof that its Host can answer a query.

## 3. Prove a semantic connection

From a project whose build code you trust, run:

```shell
kast query --name DECLARATION_NAME --fields name,location --json
```

Replace the name with a declaration in your project. Check its file and the completion evidence.
The first explicit semantic request grants trust to the exact canonical workspace root, creates private state, and prepares its Host.
A sibling worktree has a separate root and trust record. Discovery and session hooks do not grant trust.

## Private workspace state

Each workspace has a private `HOME`, IDE profile, and default Gradle home.
This is process and profile separation, not an OS sandbox. Build code runs with your user permissions.

Saved installation or workspace settings can select an external Gradle home through `GRADLE_USER_HOME`.
Inherited credentials remain available to the build. Treat an external Gradle home as trusted input: it can contain credentials, properties, and init scripts.

### Optional dependency sharing and index seeding

`KAST_WORKSPACE_DEPENDENCY_SHARING` accepts exactly `PRIVATE` (the default) or `SHARED`.
It supports saved installation and workspace configuration and takes effect only when a workspace container is first created.
Changing it does not convert an existing container. Upgrades, generation rebuilds, and repair do not seed existing containers.

| Policy | `GRADLE_USER_HOME` | Gradle home recorded at creation | Index seeding |
| --- | --- | --- | --- |
| `PRIVATE` | Unset | `<container>/state/home/.gradle` | Not requested. |
| `PRIVATE` | Set | The selected canonical directory. | Not requested. |
| `SHARED` | Unset | Kast-owned `kast-workspaces/shared/gradle`. | Attempted. |
| `SHARED` | Set | The selected canonical directory. | Attempted. |

`SHARED` does not select your `~/.gradle` unless you explicitly choose it through `GRADLE_USER_HOME`.
Each Host retains its private HOME and IDE profile. Dependency sharing does not share live index storage.

Index seeding clones an IDE system directory from a stopped, compatible workspace into a new container with copy-on-write storage.
The donor can belong to another repository. Its runtime archive, platform, and canonical Gradle home must match.
Initial clone support is limited to macOS APFS on the same filesystem. There is no full-copy fallback.
If no donor qualifies or cloning is unsupported, creation continues empty.
A clone failure also continues empty, but only after partial clone cleanup succeeds; failed cleanup rejects creation.

A seed is a starting point, not freshness evidence. The Host still scans, imports, and validates before semantic readiness.
Phase 1 native qualification and performance measurements remain pending; historical seeding experiments are not current performance proof.
See [seed outcomes](/reference/lifecycles#workspace-index-seeding) and [passive status](/reference/management#1-check-the-installation) for the recorded result.

Queries use the installed runtime and never consult release servers for an update.
Gradle import and dependency resolution can still require network access.
There is no public container creation, archive import, or desktop fallback step.

## Host heap size

`KAST_HOST_MAX_HEAP_MIB` sets the managed Host's maximum JVM heap in whole MiB from 1024 through 32768.
For example, `KAST_HOST_MAX_HEAP_MIB=8192` selects 8 GiB. An invalid value rejects the configuration.
The setting supports saved installation and workspace configuration.

If the setting is absent, Kast first looks for `-Xmx` in the private IDEA profile's copy of the bundled VM options file.
The copy must use the bundled file's name. Kast reads only its heap setting.
If the copy supplies no `-Xmx`, Kast uses the bundled heap. If both sources lack `-Xmx`, Kast uses 1536 MiB.
The selected file must specify at most one `-Xmx` with a positive, whole MiB value.
Desktop and Toolbox profiles are outside the managed Host's private profile.

Each launch writes one `-Xmx` to the private `host.vmoptions` file and records its source in `launcher.log`.
A running Host keeps its heap. To apply a change, run `kast stop --all` before the next query.

## Optional idle shutdown

`KAST_HOST_IDLE_SHUTDOWN` defaults to `off`: managed Hosts keep running until stopped.
Set it to a whole number of minutes from 5 through 1440 to let an idle Host stop itself.
For example, `KAST_HOST_IDLE_SHUTDOWN=30` selects 30 minutes.
The setting supports saved installation and workspace configuration. It takes effect at the next Host launch, not on a running Host.

Admitted requests and native work reset the idle clock. Preparation, Gradle import, and indexing prevent idle shutdown.
The Host checks every 30 seconds and stops through its existing settlement path only when work is settled.
The next explicit semantic request can start it again; passive session hooks cannot.

Allow about 26 to 28 seconds to the first query after an idle stop when existing indexes remain usable.
The macOS ARM64 check reported in [PR #1225](https://github.com/amichne/kast/pull/1225) took 27.8 seconds and re-indexed no files.
That observation used one workspace and a 5-minute limit before the final fencing fix; other restart times can differ.

See [Host shutdown and exit records](/reference/lifecycles#managed-host-idle-shutdown) for `state/host-exit.json` and its evidence limits.
