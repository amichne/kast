Kast verification is intentionally bounded. A check exists to prove a named
invariant at the narrowest faithful boundary. CI and release machinery do not
rehearse general product lifecycle behavior merely because they can.

## Verification rings

Use the smallest check that can disprove the change, then widen only when the
changed boundary requires it:

| Ring | Typical evidence | What it proves |
| --- | --- | --- |
| Focused | One module test or targeted test class | A specific domain invariant or regression. |
| Owning module | Module `test` and `check` tasks | Compilation, tests, and module-local policy. |
| Architecture | `verifyKastArchitecture` | Admitted modules, dependencies, roles, and compiled effects. |
| Product assembly | `assembleSidecarRelease` and distribution checks | Control and semantic-runtime artifacts are coherent and physically separated. |
| Installed product | `installedProductTest` | The staged product has the expected package shape and basic executable boundary. |
| Documentation | Registry generation, LikeC4 check, docs contract, and `mint validate` | Published commands, claims, links, pages, and diagrams match their authorities. |

A broader check does not substitute for a missing focused invariant. Runtime,
performance, resource, corruption, upgrade, and lifecycle scenarios belong in
focused tests or explicit investigations when they address a demonstrated risk;
they are not standing release prerequisites.

## Installed product proof

`productBuildGate` builds and checks every Gradle module, verifies architecture,
and runs one bounded packaging smoke through `installedProductTest`.

That smoke proves the staged control and semantic-runtime artifacts can be
assembled and invoked through the installed-product boundary. It does not claim
to prove repository-scale semantics, process lifecycle convergence, performance
ceilings, mutation recovery, broker behavior, or every supported environment.
Those properties remain owned by their focused implementation tests.

Release assets also include the machine-readable CLI schema and module
knowledge. Module knowledge binds generated architecture evidence and repository
guidance for agents; it is not a second semantic authority.

## Enterprise acceptance

There is no standing enterprise-acceptance gate. The previous multi-module
end-to-end harness, lifecycle replay, performance ceilings, resource sampling,
and corruption scenarios were removed from CI and release authority. Reintroduce
one only when a concrete invariant cannot be proven at a narrower boundary.

## CI admission

Pull-request and main CI detach the exact candidate SHA and run
`.github/scripts/ci/verify-checks.py`. The script admits the clean source and
executes `productBuildGate` under Java 25.

The required CI path deliberately avoids repository-scale IntelliJ acceptance,
end-to-end lifecycle drivers, timing/resource observation, corruption rehearsal,
compatibility replay, and publish verification. Those mechanisms added cost and
failure surface without establishing distinct release invariants.

## Release admission

A manually dispatched candidate build on `main` uses
`.github/scripts/release/build-assets.sh` from the exact detached source revision.
It runs `productBuildGate`, builds the release archives, emits the CLI schema and
module knowledge, generates the SBOM, and records SHA-256 files for each
published asset.

The release workflow only admits a successful candidate run for the exact
current `main` SHA and reviewed candidate version. It downloads those retained
artifacts and publishes the same bytes. It does not rebuild the product or run a
second behavioral qualification pass.

The release invariant is therefore:

```text
exact main revision
  -> productBuildGate passes
  -> release artifacts are generated from that revision
  -> artifact checksums are retained
  -> those retained artifacts are published
```

Publication still refuses an existing tag or release and requires the release
commit to equal `origin/main`.

## Release integrity

The wrapper distribution has a SHA-256 pin and URL validation. Gradle verifies
dependency artifacts and metadata against `gradle/verification-metadata.xml` in
strict mode. Release builds never regenerate those checksums automatically.

The SBOM generator downloads a checksum-pinned Syft archive, scans the two
product archives, records the source revision and archive digests in the
CycloneDX document, and fails if either archive changes during the scan.

Actions remain pinned to full commit identities. The release workflow does not
claim that additional attestation, upload/download replay, timing evidence, or
lifecycle rehearsal strengthens the product; those were removed from release
authority.

## Reproduce CI locally

Routine CI needs macOS arm64, Python 3.12, and Java 25. From a detached clean
checkout, run:

```shell
export KAST_RELEASE_JDK_25="/path/to/jdk25"
python3 .github/scripts/ci/verify-checks.py
```

To build the exact candidate artifacts without publishing:

```shell
bash .github/scripts/release/build-assets.sh \
  --version "$(cat distribution/release/candidate-version.txt)" \
  --source-revision "$(git rev-parse HEAD)"
```

## Keep this specification authenticated

The documentation workflow forms its own proof chain:

```text
CanonicalOperation and command graph
  -> generated operation registry
  -> generated CLI reference

LikeC4 source and locked generator
  -> provenance-checked web-component bundle
  -> embedded technical views

Source authorities and Mintlify navigation
  -> docs/test_public_docs.py
  -> mint validate
```

When mechanics change, update the source contract first. Regenerate derived
artifacts with their owning task, update only the affected explanation, and add
or strengthen a docs assertion for any claim whose drift would mislead a
maintainer. Do not patch generated CLI or LikeC4 output by hand.

Every public page declares bounded `code_sources` in its OKF header. Ask which
pages cite a changed authority before editing prose:

```shell
python3 docs/test_public_docs.py --impact path/to/changed-source.kt
```

## Contributor path

<Steps>
  <Step title="Name the invariant and owner">
    Identify the boundary input, trusted domain value, finite failure set,
    package or module owner, and executable proof that can fail before the fix.
  </Step>
  <Step title="Orient through contracts">
    Start at the canonical operation or domain contract, then follow service,
    adapter, composition, wire, and CLI projections only as far as the change
    requires.
  </Step>
  <Step title="Prove the narrow behavior">
    Add the smallest public-behavior test, observe the intended failure, and
    implement the narrowest typed transition that makes it pass.
  </Step>
  <Step title="Widen only when required">
    Run owning-module and architecture checks, then packaging or documentation
    verification only when the changed surface crosses those boundaries.
  </Step>
  <Step title="Leave an authority trail">
    Keep durable rationale in contracts, tests, architecture policy, or this
    specification. Generated artifacts must retain their provenance.
  </Step>
</Steps>

## Primary authorities

- The [root Gradle build](https://github.com/amichne/kast/blob/main/build.gradle.kts)
  owns product assembly and the bounded `productBuildGate`.
- [`test-installed-product.sh`](https://github.com/amichne/kast/blob/main/packaging/test-installed-product.sh)
  verifies the staged product packaging boundary.
- [`build-assets.sh`](https://github.com/amichne/kast/blob/main/.github/scripts/release/build-assets.sh)
  builds retained release artifacts from an exact admitted source revision.
- [`test_public_docs.py`](https://github.com/amichne/kast/blob/main/docs/test_public_docs.py)
  binds public pages, claims, navigation, authorities, and architecture embeds.
- The [documentation workflow](https://github.com/amichne/kast/blob/main/.github/workflows/docs.yml)
  regenerates and validates the published documentation surface.
