1. Executive conclusion

jetbrains-index-mcp-plugin is a valid and useful functional reference. Its interface is responsive because the common path stays inside an already-running IntelliJ process and calls the same indexed navigation and semantic APIs that power the IDE. It scopes work early, runs PSI work in cancellable read actions, limits projection, paginates large results, fails on dumb mode instead of guessing, and keeps native refactoring execution on the EDT. Those are concrete approaches Kast should reuse.

It is not an architecture to copy wholesale. The reference project is a single IntelliJ plugin with an MCP transport, accepts several discovery-oriented input shapes, holds short-lived in-process state, and often performs a complete operation in one request. Kast needs stronger boundaries because its purpose is not only IDE automation. Kast must support exact, generation-bound, composable evidence and durable mutation workflows for agents.

The program therefore adopts a dual substrate:

Substrate Authority Lifetime Examples
IntelliJ live substrate Current platform state one read, command, or runtime epoch VFS, Project Model, indexes, PSI, Kotlin Analysis API, reference searches, diagnostics providers, refactoring processors
Kast durable evidence substrate Proof about one admitted repository state generation, continuation, plan, attempt, receipt exact selectors, coverage, occurrences, graph facts, plans, obligations, before-images, terminal failures, verified receipts

The live substrate is used directly whenever it already answers the operation. The durable substrate exists only when facts must survive the request, compose across operations, prove completeness, or mediate authority. This prevents Kast from rebuilding IntelliJ while preserving the properties that make Kast distinct.

2. What this program is trying to achieve

The intended user experience is iterative:

  1. Fast reads become useful first. Warm file, symbol, definition, and one-hop relation requests run against native IntelliJ indexes under one published generation. They do not import Gradle, refresh the repository, build a graph, or write SQLite.
  2. Planning becomes useful before mutation. Add-declaration returns a stable, inspectable plan with an exact target, expected write set, obligations, and expected semantic delta.
  3. The first mutation becomes fully trustworthy. A later apply request revalidates the plan, prepares recovery, performs one short IntelliJ mutation, publishes a new generation, verifies the result, and returns a verified receipt.
  4. Rename proves the architecture at multi-file scope. Native RenameProcessor is used only after Kast has established the exact plan and authority.
  5. Other operations migrate one at a time. Each operation earns its contract, adapter, proof, and performance evidence. Aggregate compatibility is retired last.

“Usable” does not mean all target modules are active. It means each delivered operation is complete within its declared scope, fast on the ordinary path, and structurally unable to report unsupported certainty.

4. Overarching principles

ID Principle Operating rule
P01 Use the productized IntelliJ path first Before creating an index, scanner, cache, or traversal, identify the IntelliJ action or query that already serves the equivalent IDE feature. File, class, symbol, definition, reference, implementation, hierarchy, diagnostics, and rename operations should begin from those APIs. A Kast-owned implementation is justified only by a named semantic requirement that the platform path cannot satisfy.
P02 Treat IntelliJ as the live substrate and Kast as the durable evidence substrate IntelliJ owns current PSI, indexes, project model, VFS, refactoring engines, and compiler sessions. Kast owns detached identity, generation, coverage, plans, obligations, continuations, persisted evidence, and receipts. Persist only facts that must survive a request, compose across operations, or support repository-wide proof. Do not duplicate a platform index merely because Kast can.
P03 Separate discovery from exact identity Native Go to File, Class, and Symbol queries are excellent discovery mechanisms. Their display names, coordinates, and navigation items are not exact selectors. A second compiler-backed transition must issue the exact generation-bound selector consumed by downstream operations.
P04 Compile scope before starting work Module, source-set, production, test, library, generated, and exact-file scope must become a typed platform search scope before a query runs. Filtering after PSI resolution wastes work and can produce incorrect completeness claims. Gradle and IntelliJ project-model evidence outrank path inference.
P05 Bind every semantic read to one published generation A ready generation is an admitted read capability, not a Boolean. A read either completes against one generation or is rejected because the workspace moved. Ordinary reads do not refresh, import Gradle, or build evidence to make themselves ready.
P06 Use cancellable, write-allowing read actions Long PSI and index reads use IntelliJ coroutine read actions, check cancellation within processors, and never swallow dumb-mode or cancellation exceptions as empty or complete results. Short reads remain small enough to restart when a write arrives.
P07 Do not hide cost escalation A metadata or index lookup cannot obtain Gradle import, graph build, SQLite write, or source write authority. Missing prerequisites return a typed blocker or explicit next operation. Physical module classpaths and operation-specific capabilities enforce this rule.
P08 Do not refresh the repository on the normal read path The reference plugin makes external-change synchronization optional because a recursive root refresh is expensive. Kast already has a stronger event-driven transition and coverage model. A read consumes the current generation; a source event requests a targeted transition. Recovery audit is not a per-call tax.
P09 Bound the projection without lying about completeness Limit result records, bytes, previews, and continuation state. Report exact counts only when enumeration is proven terminal. A cap, cancellation, dumb-mode transition, stale cursor, unsupported element, or provider failure produces qualified or rejected output, never complete output.
P10 Reserve registered operations for work that inherently outlives a request Normal file, symbol, definition, and one-hop relation reads remain synchronous within a bounded request. Workspace import, graph build, project diagnostics, large planning, and mutation transition may use a registered operation with a durable identifier, operation deadline, bounded polling, and exactly-once cleanup.
P11 Use native refactoring as the physical executor, not as the workflow owner Kast plans and proves; IntelliJ mutates. Planning and search finish before the EDT command. The write action contains only the operation-specific PSI or refactoring call. Kast still requires approval, revalidation, recovery evidence, write-set closure, a resulting generation, and operation-specific verification.
P12 Make misuse mechanically unavailable Contracts, services, IntelliJ adapters, SQLite adapters, filesystem adapters, transport, and composition are distinct Gradle modules. A caller receives only its operation capability. It never receives Project, AnalysisBackend, a database, a runtime, or a service container from which stronger authority can be recovered.
P13 Admit expensive work according to resource state Stagger startup and import initiation, separate initiation from readiness wait, cap concurrency, expose heap and queue pressure, and fail closed before GC thrash or EDT starvation. Resource admission is explicit evidence, not an incidental exception.
P14 Preserve proof through every boundary A successful parse, lookup, scope admission, selector resolution, generation admission, writability check, or recovery preparation returns a stronger type. Callers consume that value; they do not unpack it to primitives and reconstruct its proof later.
P15 Benchmark work, not impression The reference project is a valid functional example, but it does not publish an apples-to-apples latency comparison with Kast. Every performance decision must record operation latency, queue time, smart-mode wait, index work, PSI work, result count, bytes, page count, refresh/import activity, and whether a new generation was built.

7.1 The ordinary read performance contract

A stable-generation read must satisfy all of these mechanical conditions:

  • zero Gradle import;
  • zero workspace publication;
  • zero graph build;
  • zero SQLite write;
  • zero recursive content-root refresh;
  • one typed search scope compiled before the query;
  • one or a small bounded sequence of cancellable read actions;
  • streaming native processors with cancellation checks;
  • bounded result records and bytes;
  • exact generation and completeness in the result;
  • separate timing for admission, native query, semantic resolution, projection, serialization, and IPC.

If any prerequisite is missing, the handler returns a typed blocker. It does not perform the stronger operation itself.

7.2 When persistence is justified

Persist a fact only when at least one condition is true:

  1. The fact must survive the producing request or process.
  2. The fact is required by a later compatible operation without reconstructing identity.
  3. The fact participates in repository-wide completeness or negative proof.
  4. The fact is expensive enough that reuse is measured and invalidation is sound.
  5. The fact is part of a durable plan, attempt, recovery record, or receipt.

File names, class names, symbol candidates, a single definition, and many one-hop reads usually do not meet this bar. Exact selectors, relationship coverage, repository graph facts, source generations, plans, and receipts do.

8. Architecture corrections before extraction

The current architecture firewall is valuable and should remain. Four corrections are required before it becomes the implementation program:

  1. Alternative lanes must be executable semantics. Semantic and external apply are one-of branches, not two mandatory predecessors.
  2. Dependency direction must follow ports. Services consume contracts and SPIs; adapters implement SPIs; persistence implements an evidence contract; the registry imports feature contracts.
  3. Migration needs a transition topology. Exact legacy-to-target edges are temporary, retirement-bound, and shrink-only. Target-to-legacy edges remain impossible.
  4. Backend retirement must be split. Mutation methods can become transport compatibility bindings after mutation slices migrate. The full AnalysisBackend type disappears only after read, relation, graph, diagnostic, workspace, and evidence families migrate.

These corrections preserve the firewall’s intent while avoiding a horizontal waterfall in which no operation becomes usable until the entire platform exists.

10. Ticket contract

Each ticket below is intended to become one .agent/TASK.md-style work packet. Before implementation, the agent must replace broad owner names with exact allowed read and write paths and name the focused current test that supplies the red proof. A ticket may add the target test task when the target module does not yet exist, but it may not broaden the ticket goal.

The ticket is complete only when:

  • its one observable outcome exists;
  • the red proof fails before the change and the green proof passes after it;
  • every established fact is carried by a stronger value or capability;
  • no new bypass, fallback, effect allowance, or incidental cleanup entered the change;
  • the architecture projection and exact baseline are updated together;
  • direct consumers pass the narrowest widening proof;
  • the evidence ledger points from the ticket to its executable proof.

KIP-001 — Freeze the source and performance ledger

Milestone: M0
Depends on: None
Reference basis: KAST-PERF, JB-README, P15

Goal

Create one checked-in ledger that binds this program to exact Kast, reference-project, IntelliJ build, corpus, machine, operation, and benchmark identities.

Why this ticket exists

The reference project is useful as functional evidence, but “snappy” is not a reproducible acceptance condition. Kast already has a 0.73 s warm-search median from #604; that evidence must become the baseline rather than disappear into narrative.

Allowed scope

  • Record exact revisions and supported IDE builds.
  • Define representative corpora: Kast, a medium multi-module Kotlin repository, and an enterprise-shaped corpus.
  • Capture warm and cold traces for file discovery, symbol discovery, definition, references, workspace admission, and add-declaration planning.
  • Record stage timing and work counters, not only wall time.

Non-goals

  • Changing production behavior.
  • Choosing an optimization before evidence identifies the cost.
  • Claiming the reference project has a specific latency without measuring it.

Red proof

A performance change can be proposed without an exact prior sample, operation identity, corpus identity, or work breakdown.

Green proof

A deterministic ledger validator rejects missing provenance, incomparable runs, and unsupported claims; the baseline commands reproduce the recorded samples.

Done when

  • The ledger names every source revision and environment input.
  • Every later performance ticket references one baseline operation.
  • Warm search evidence from #604 is retained as historical evidence, not rewritten as a new claim.

KIP-002 — Correct branch, join, and recovery semantics

Milestone: M0
Depends on: KIP-001
Reference basis: KAST-ARCH, P11, P14

Goal

Replace the flat mutation process DAG with a model that represents one-of semantic or external apply lanes and recovery as an interrupt edge available after recovery preparation.

Why this ticket exists

The current executable graph makes the post-apply step depend on both apply lanes even though the prose declares them alternatives. Recovery is also modeled as a final dependency instead of a failure transition.

Allowed scope

  • Add explicit branch and selected-lane join semantics to build-logic policy.
  • Model recovery from every post-recovery-preparation state.
  • Generate the same semantics into the review projection.
  • Add negative tests for an AND-join across mutually exclusive lanes.

Non-goals

  • Implementing either source writer.
  • Changing the public mutation protocol.
  • Adding operation-specific plan types.

Red proof

The policy accepts a process graph in which RP12 requires both RP11S and RP11E, or in which a failure after recovery preparation has no recovery edge.

Green proof

Policy tests prove exactly one selected apply lane reaches the common suffix and every admitted failure reaches RolledBack or RecoveryRequired.

Done when

  • The Kotlin policy is the sole authority.
  • The JSON projection is deterministic.
  • No target module must execute both source-write lanes.

KIP-003 — Correct module dependency direction

Milestone: M0
Depends on: KIP-001
Reference basis: KAST-ARCH, SLOP-RATCHET, P12

Goal

Make contracts and SPIs the dependency center: services depend on ports, physical adapters implement ports, the registry imports operation contracts, and persistence implements an evidence contract.

Why this ticket exists

Several planned edges currently invert control: services depend on SQLite or filesystem implementations, an IntelliJ adapter depends on its service, and change contracts depend on the registry. Those edges make physical effects reachable from orchestration code.

Allowed scope

  • Introduce :workspace:spi, :evidence:contract, and :change:recovery:spi or equivalent exact ports.
  • Reverse adapter-to-service and contract-to-registry edges.
  • Keep composition as the only complete implementation owner.
  • Add graph fixtures for each forbidden inverse edge.

Non-goals

  • Moving product implementations.
  • Activating all target modules.
  • Creating a generic repository or service locator.

Red proof

A service can depend directly on :evidence:sqlite or :change:recovery:filesystem, or a feature contract can depend on :protocol:registry.

Green proof

verifyKastArchitecture rejects each inverted edge and accepts the corrected acyclic graph.

Done when

  • Every physical adapter depends inward on a contract and SPI.
  • No contract imports a registry, service, adapter, JDBC, IntelliJ, Gradle, or filesystem writer.
  • The correction is in executable policy, not documentation only.

KIP-004 — Introduce retirement-bound migration edges

Milestone: M0
Depends on: KIP-003
Reference basis: KAST-ARCH, P12

Goal

Permit an exact legacy host to consume an exact target contract, SPI, or service temporarily, with one mandatory retirement ticket and no target-to-legacy edge.

Why this ticket exists

Without a transition topology, each extraction must move contracts, implementations, composition, and all consumers in one change. That recreates a big-bang migration.

Allowed scope

  • Define temporary migration edges separately from permanent allowed edges.
  • Require an exact consumer, dependency, retirement ticket, and lifecycle state.
  • Make the edge invalid after its retirement ticket completes.
  • Require the temporary set to shrink.

Non-goals

  • Allowing target modules to depend on legacy hosts.
  • Wildcard migration permissions.
  • Using a baseline allowance as a permanent architecture edge.

Red proof

A legacy host cannot delegate to a new target service without either an unlisted edge or a one-change full cutover.

Green proof

A fixture admits one exact temporary legacy-to-target edge, rejects every reverse or wildcard edge, and rejects an edge whose retirement task is absent or complete.

Done when

  • Each migration edge has one owner and one retirement ticket.
  • The final graph remains unchanged.
  • No compatibility implementation is created without a named removal point.

15. Program completion condition

This program is complete when:

  • ordinary reads use native IntelliJ indexes and scoped semantic APIs without hidden expensive work;
  • exact selectors, coverage, continuations, plans, attempts, and receipts remain generation-bound and proof-carrying;
  • only registered long work outlives a request;
  • only workspace adapters can refresh/import and only source-write adapters can mutate;
  • add-declaration and rename reach verified receipts or truthful terminal failures;
  • external files use a separate typed lane;
  • raw semantic apply is unavailable;
  • the server depends on contracts and bindings only;
  • no internal implementation consumes AnalysisBackend;
  • each performance claim has comparable evidence;
  • the enterprise acceptance journey cannot represent partial, stale, truncated, ambiguous, unsupported, or unverified evidence as complete.

The target is not “more modules.” The target is a usable sequence of narrow operations where IntelliJ does the platform work it already performs well and Kast adds only the durable semantic control surface that IntelliJ does not provide.
