Direct MCP carries Kast tool calls over stdio. The client starts the process from the intended repository directory and admits its catalog after negotiation.

## Catalog

`tools/list` supplies each tool's name, `inputSchema`, and `outputSchema`. Those installed schemas govern the session.

| Tool | Purpose |
| --- | --- |
| `query_symbols` | Declarations, source, relationships, and composition. |
| `check_diagnostics` | IDEA diagnostics for a path. |
| `health_check` | Workspace binding and readiness. |
| `add_declaration`, `replace_body` | Targeted source changes. |

Direct MCP omits `workspace_lifecycle`. Hosted App Server supplies that separate project-control tool.

Tool discovery establishes available operations. It does not establish readiness of the IDEA project or completion of a semantic query.

## Call and result

`tools/call` selects a catalog tool and argument object. This example requests readiness rather than declaration evidence.

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {"name": "health_check", "arguments": {}}
}
```

The reply separates display text in `content[]` from admitted `structuredContent`. `isError` reports tool-call failure.

For semantic tools, `structuredContent` is the canonical operation document. Its own status reports semantic completion, qualification, or rejection.

An invocation failure can omit the operation document. `health_check` uses a separate readiness shape with its own schema.

Clients must decode the wrapper and selected tool document separately. A successful JSON-RPC exchange cannot strengthen an incomplete semantic answer.
