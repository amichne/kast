`tools/list` exposes installed tools and schemas after MCP negotiation. The MCP process uses stdio from the client's repository directory.

Each catalog entry defines a tool name, `inputSchema`, and `outputSchema`:

| Tool | Purpose |
| --- | --- |
| `query_symbols` | Declarations, source, relationships, and composition. |
| `check_diagnostics` | IDEA diagnostics for a path. |
| `health_check` | Workspace binding and readiness. |
| `add_declaration`, `replace_body` | Targeted source changes. |

Direct MCP omits `workspace_lifecycle`. Hosted App Server supplies that tool separately.

## Call and result

`tools/call` accepts a catalog tool name and its arguments. This example calls `health_check`:

```json
{
  "jsonrpc": "2.0",
  "id": 2,
  "method": "tools/call",
  "params": {"name": "health_check", "arguments": {}}
}
```

For a semantic query, select `query_symbols`. Use [Query forms](/reference/api) to choose its arguments.

The JSON-RPC result carries `content`, `isError`, and admitted `structuredContent`. For semantic tools, `structuredContent` contains the canonical operation document. That document preserves status, references, coverage, failures, and recovery evidence.

`isError` describes tool-call failure. The operation document separately reports its semantic status. An invocation failure can omit the structured document. `health_check` uses its own readiness schema.

The [wrapper](/reference/models/mcp-tool-call-result) and tool-specific [operation document](/reference/schemas) have separate schemas. OpenAPI `/callables/…` labels identify documentation sections. Kast does not expose them as HTTP endpoints.
