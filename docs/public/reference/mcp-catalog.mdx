The installed Kast MCP server exposes tools through `tools/list` and accepts
their JSON inputs through `tools/call`. Your client's live `tools/list` result
contains the exact names, descriptions, and input schemas for its release.

## Available tools

| Purpose | Tools |
| --- | --- |
| Search and diagnostics | `search_classes`, `search_functions`, `search_declarations`, `check_diagnostics` |
| Read and explore | `query_symbols`, `source_read` |
| Candidate inspection | `symbol_lookup`, `symbol_inspect` |
| Check the workspace | `health_check`, `validate_workspace` |
| Change source | `change` |

`health_check` reports the bound workspace and IDEA readiness.
`validate_workspace` runs requested read only probes and reports each probe's
outcome. Neither establishes that every future semantic request will succeed.
The `change` tool is a write operation; see [Change source](/change).

## Tool inputs

The generated callable pages in this tab describe shared operation inputs and
canonical result models. Their hosted response envelope differs from the MCP
result wrapper below. `POST /callables/...` labels organize documentation;
Kast does not expose those paths as an HTTP service. Use `tools/list` for the
exact MCP input schema, including the two workspace investigation tools. The
App Server also exposes `workspace_lifecycle` for explicit project control;
it is not in the direct MCP catalog.

## Read the result

For semantic reads, MCP returns a human summary and a machine envelope in
`structuredContent`. The canonical document is also available as text. A
`complete` answer covers its declared scope; `partial` carries a limit or stop
reason; a rejected result is not an empty successful search. Keep returned
references unchanged. [Read a response](/reference/responses) has examples.
